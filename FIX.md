# Fix Log

> Rotated daily into `docs/archive/fix-log/` — see [INDEX.md](docs/archive/fix-log/INDEX.md) for older entries.

## Conxa Execute no longer has its own separate account system or backend — it now runs entirely on the same one as everything else — 2026-09-17
Conxa Execute used to be its own little island: its own sign-in system, its own payment setup, its own way of letting people pay with their own AI key. That meant extra accounts to create, extra bills to pay, and a clunky "type in this code" step for anyone a company wanted to give access to. All of that is gone. Execute now signs in with the exact same company account as everything else, its cost comes out of the same shared credit balance a company already has, and giving someone access is as simple as inviting them by email — the moment they sign in, they're in, no code to copy or paste. A signed-in person can also now switch between using it on their own or on behalf of a company they belong to. One loose end remains: a couple of one-time account-setup clicks still need to happen before this goes live, tracked so nothing gets missed.

## Conxa Execute cleaned up: dead code removed, and several places that used to fail silently now tell you what went wrong — 2026-09-17
Conxa Execute had grown some leftover parts and a habit of hiding errors instead of showing them. We removed a large chunk of unused reference code that was never actually running (about 60 files copied in "just in case" for a future upgrade, and a whole set of screens and buttons that could never actually be reached), which makes the app smaller and easier to maintain without changing how it works. More importantly, we fixed several spots where something going wrong used to look like nothing happening at all: if the app failed to start up properly it used to show a permanently blank window with no explanation — now it shows a real message and a Retry button. If the list of available skills failed to load, it used to just say "no skills installed" as if that were the truth — now it says the actual problem occurred, instead of a wrong but confident-sounding answer. A corrupted history file used to get silently wiped and replaced with a blank one — it's now set aside instead, so nothing is lost. We also closed a real billing safety gap: one of the payment-confirmation messages from our payment provider could previously be accepted without checking its signature, meaning a forged message could have looked genuine — every payment confirmation is now always checked.

## Clicking "Sign in" in Conxa Execute now tells you why it isn't working, instead of doing nothing — 2026-09-17
In the first real installed copy of Conxa Execute, clicking "Sign in with CONXA" did nothing at all — no message, no browser window, nothing. That's because the sign-in system for this particular app hasn't been fully connected on the company's end yet, but the button was designed to only react on success and stayed silent on any failure, like a doorbell that's wired up but not yet hooked to a chime. It now shows a plain message explaining sign-in isn't set up yet, in both places the button appears. Actually finishing the sign-in connection is a separate step that needs a company account to be created and linked in.

## Conxa Execute can now be installed as a real Windows app, not just run from source — 2026-09-17
Until now, the only way to use Conxa Execute was for a developer to check out the code and start it by hand — there was nothing to actually give a customer. Now there's a proper installer, built the same way Build Studio's already is: download it, click through a quick setup, and it puts a normal desktop app on your machine with its own icon and Start Menu shortcut. It also updates itself quietly in the background — when a new version comes out, it downloads next time you're online and finishes installing the next time you close the app, with no pop-ups or prompts to deal with.

## Conxa Execute now shows the browser inside the app itself, instead of popping open a separate window — 2026-09-17
Running a skill from Conxa Execute used to open a whole separate Chromium browser window that sat on top of the app, disconnected from the chat. Now, when a skill runs, a panel slides in on the right side of the same window and shows the live page there — chat on the left, the browser working on the right, one window instead of two. It's fully interactive: you can click and type directly in that panel the same as any browser. If several skills run at once, each gets its own tab inside that one panel instead of its own window. This landed in two parts today: first the skill-running part, then signing in to a website and handing control to a person mid-run — both of those also now happen right in the same panel instead of opening their own window. Every other way of running a skill (Claude Desktop, scheduled runs) is completely unaffected — they still work exactly as before, and if anything goes wrong showing the panel, the run quietly falls back to the old separate-window behavior instead of failing.

## Conxa Copilot no longer says "I didn't have a response" when it actually did the work and just got cut off — 2026-09-16
Asking Conxa Copilot a question like "Why did this workflow fail" could come back with a generic "Copilot didn't have a response for that" message that made it sound like the question was the problem. It wasn't — the AI provider was quietly spending its entire writing budget on invisible "thinking" and running out of room before it ever wrote the actual answer, like someone who talks themselves through a math problem out loud and then walks away before saying the final number. We closed two more gaps in the same area: this could also happen on Copilot's other, structured-answer request (previously only guarded on one of its two request types), and it could happen silently — the system had no way to notice on that structured request when it had happened, so the reviewer just saw an empty answer with no explanation. Both requests now get much more writing room as a safety margin, and the system now recognizes and clearly logs this specific failure everywhere it can occur, not just the one place it was caught before.

## Workspace admins can now hand out Conxa Execute seats, and invitees can redeem them — 2026-09-16
A workspace admin can already sponsor Conxa Execute access for people who don't use Build Studio, with the cost coming out of the workspace's shared AI Usage Credits — but there was no screen to do it from, and no way for the invited person to actually claim their seat. Now there's an "Execute Seats" panel on the Team page where an admin types an email, gets an invite link, and can revoke a seat later. The invited person opens that link, gets a plain instructions page with their invite code, and pastes it into Conxa Execute's Settings to redeem it — after which their chat is clearly marked "Paid by [workspace name]" instead of asking them for a card or a key. We also caught and fixed a mismatch that would have made claiming silently fail: the invite link originally pointed at a claim button on the wrong sign-in system, one that Conxa Execute can't see — like a gift card that only worked at a different store than the one on the card.

## Conxa Execute's light theme now actually works, and a dead button is gone — 2026-09-16
The Settings screen in Conxa Execute had a "System / Light / Dark" theme switcher that didn't do anything — clicking any of the three options had no effect, and a note under it admitted "v0.1 is dark only." There was also a "Manage billing" button next to Sign out. Both are fixed: "System" is gone, and clicking "Light" or "Dark" now actually switches the whole app's colors right away and remembers your choice the next time you open it. The "Manage billing" button has been removed.

## Stopped wasting money re-asking a question the AI had already fully answered "in its head" — 2026-09-16
While investigating yesterday's Copilot fix, we found a related problem: sometimes the AI spends its entire thinking budget reasoning through an answer and never actually writes the words down, even though it worked the whole way through and we still paid for that work. The system couldn't tell that apart from the AI simply being unreachable, so it would ask the exact same question two more times, tripling the cost for no benefit, before giving up with a confusing "all providers failed" message. Now the system recognizes this specific situation, stops after one try instead of three, and logs it clearly instead of blaming a working AI connection. We also told the AI not to bother "thinking out loud" for these particular quick-reply questions, since it doesn't need to, which should make this happen far less often. Leftover troubleshooting logs from yesterday's investigation were also cleaned out.

## Conxa Execute now requires signing in before you can use it — 2026-09-16
Previously, Conxa Execute (the separate chat-style app for running automations) would open straight into the main screen, letting someone poke around before ever signing in. Now the app shows a "Sign in to CONXA" screen first, and the rest of the app stays hidden until that's done — like a building where the lobby doors don't open until you badge in, instead of leaving them propped open. This closes a gap where someone could reach parts of the app without an account attached to them.

## Simplified the "chat mode" picker out of Conxa Execute's settings — 2026-09-16
The Settings screen in Conxa Execute used to have a three-way switch (bring your own key, pay-as-you-go top-up, or subscription) with an explanation of what each one did. That switch and its explanation are now gone from the screen; which mode is used is decided elsewhere instead of by clicking a button in Settings, so the settings screen is shorter and less confusing.

## Fixed the Conxa Copilot going completely silent after a question — 2026-09-16
Asking the review assistant a question would sometimes leave the question sitting on screen with no answer and no explanation, even though the AI had actually written one and we were billed for it. The assistant asks the AI twice per question — once for the answer it types out live, once for its repair suggestions — and if the first request came back empty, the whole thing was abandoned before the second one ever ran. It's like hanging up on a call because the first hello didn't come through, instead of just saying "hello?" again. Now an empty first reply quietly falls through to the second request, which almost always has the answer. Two related fixes came with it: the AI is given more room to think before it has to start writing (it was running out of room mid-thought and producing nothing), and when a question genuinely can't be answered, the reason now stays in the conversation instead of flashing by in a notification that disappears — and it no longer wrongly blames the user's internet connection when the connection was fine.

## Companies can now hand out access to Conxa Execute, paid from their existing plan — 2026-09-16
Until now, a company's Build Studio plan and Conxa Execute (the separate chat-style app for running automations) had nothing to do with each other — anyone using Execute had to pay for it themselves. Now a company's plan also comes with a number of Execute seats they can hand out to people — even people who never touch Build Studio at all, like a customer support team — just by sending them an invite link with an email address attached. Free plans get 1 seat, Starter gets 25, Pro gets 100. Anyone using one of those seats has their usage paid for automatically out of the company's own shared pool of AI credits, instead of needing their own subscription. That shared pool used to be called the "Human Edit pool" and only powered one small part of Build Studio's editor; it's now renamed "AI Usage Credits" everywhere customers see it, since it covers this new Execute usage too.

## Gave the Conxa Copilot a much bigger picture of a workflow, and real editing hands — 2026-09-16
The behind-the-scenes assistant that helps reviewers fix a broken automated workflow (still not visible to customers yet) used to be shown every tiny technical detail of every single step, every time it answered a question — like handing someone the entire filing cabinet just to answer one question about one folder. Now it gets a short summary of the whole workflow up front, and can ask for the specific details it actually needs, when it needs them — a screenshot, the exact page-matching rules for one step, the history of past edits. It also used to be able to change only a handful of small things about a step, like a note or a value. It can now propose bigger changes too — adding a whole new step (like a pause-and-check moment, or a "hover over this first" step), removing one, or moving one — as long as every such change is backed by something it actually saw, and it's still never allowed to invent how the workflow finds a button or field on the page; it can only reuse an address the recording already captured. Every proposal still has to be approved by a person before anything changes, and if several changes are approved together, one "undo" now reverses the whole group at once instead of requiring several undos. Finally, it now remembers the last conversation about a workflow instead of forgetting everything the moment the review window is reopened.

## Added a way for a workflow to pause and hand control to a person, then pick back up automatically — 2026-09-15
Some steps genuinely can't be automated — a two-factor login code, a "prove you're human" puzzle, signing a document. Until now, a workflow that ran into one of those had to stop and fail. Now a workflow can include a "hand over to a person" step: it pops up a banner right on the screen the workflow is looking at, saying what's needed, with a "Done" button. The person does the tricky bit themselves, clicks the button, and the workflow picks up exactly where it left off — same browser window, same page, nothing restarted. If the person is away, the workflow waits for them (instead of tying up the app) and resumes the moment they come back, even minutes or hours later; it can also be resumed by running one command instead of clicking the button, for anyone scripting things. It also plays nicely with other work happening at the same time: while it's waiting on a person, it steps out of the way so other workflows using the same website aren't blocked, and steps back in only once it's ready to continue.

## Finished the "AI Review" checkpoint feature: it can now actually be built and tested, not just recorded on paper — 2026-09-14
A workflow can now pause partway through, show Claude the current screen, ask it a question the workflow's author typed in ("is there an error banner on this page?"), and use the answer to decide what happens next. The engine that runs this on a customer's computer was already built in an earlier update, but nobody could actually create one of these checkpoints — there was no button for it in the Build Studio, and there was no way to test a workflow containing one before shipping it, because the test run had nobody to answer the question. Both gaps are now closed. A new "AI Review" option appears when adding a step, with a question box, a few one-click answer-shape presets (yes/no with a reason, a single answer, or "accept anything"), and a choice for what happens if a usable answer never comes back (stop the run, fall back to a default, or keep going). And when a builder tests a workflow with one of these checkpoints in it, the Build Studio now answers the question itself using its own AI connection and keeps the test running, instead of the test just failing outright. The checkpoint also now sees the same list of on-screen buttons and fields the recovery system already looks at, not just a picture of the page, so it can reason about the page more reliably.

## Fixed a sign-in that "didn't take" for group workflows until the app was restarted — 2026-09-14
A workflow that belongs to a group of connected apps (for example, an "Enterprise" folder that needs both Salesforce and Google Drive) could get stuck saying it still needed a sign-in, even right after the person had just signed back in successfully. Running the test again showed the exact same "please sign in" message — but simply restarting the Build Studio app made it work perfectly. The cause: the app keeps two copies of a saved sign-in on disk — a secure, locked copy and a plain backup copy — and it was always trusting the secure copy, even when the plain backup was the newer, correct one written moments earlier by the fresh sign-in. Only a restart happened to force the secure copy to be refreshed from the backup. Now the system always checks which copy is actually the newest and uses that one, refreshing the secure copy on the spot — so a fresh sign-in takes effect on the very next run, no restart needed.

## Fixed "something went wrong" when attaching a recording screenshot to a step inside a loop — 2026-09-14
In the workflow editor, picking a screenshot from the recording to attach to a step (or clearing one, or picking a different moment-in-time frame) would fail with a generic error, but only for a step that lives inside a "repeat for each" loop. This turned out to be two separate problems layered on top of each other. First: the app knew which loop step the person had selected on screen, but when it saved the change it only ever told the backend which loop the step belonged to, not which specific step inside that loop — like addressing a letter to an apartment building but leaving off the unit number. The backend would then try to apply the change to the whole loop instead of the one step inside it, and reject it. Second, once that addressing problem was fixed, a deeper issue surfaced: building the picture the system studies to recognize that element again was silently missing some of the photos it needed, so it failed anyway — and that failure was showing up as an unhelpful "something went wrong" instead of a clear explanation. Both are now fixed: the app sends the full, specific address for a step inside a loop, the missing photos are included again, and if this step ever does fail for a real reason, the person now sees an understandable message instead of a scary generic crash. This only affected steps inside loops; regular steps were never broken.

## Quieted a harmless but scary-looking error message during recording — 2026-09-14
While recording a workflow in the Build Studio, closing a browser tab at just the wrong moment could print a long, technical-looking error in the developer logs — something about a "closed target" and a task exception. Nothing was actually broken: the recording had already captured what it needed, and only a background cleanup message (delivering a receipt back to a page that was already gone) failed to send. That specific, expected message is now silenced so it doesn't look like a crash; any other, genuine error still shows up as before.

## Finished the compiler cleanup: a compile now shows when a background helper failed, and corrupted files can't silently vanish or lose data — 2026-09-14
This finishes yesterday's cleanup of the automation compiler. First, a compile report can now honestly say "something needs a second look" — before this, if a background double-check step (the "second opinion" that reviews a whole recorded automation) failed to run at all, the report looked exactly as clean as one where that step succeeded and found nothing wrong. Now a genuine failure is flagged, so a reviewer can tell the two apart instead of trusting a report that quietly skipped a safety check. Second, a caching bug that could get permanently stuck is fixed: three spots used to save a fallback guess into their memory as if it were a real, confident answer — meaning one brief network hiccup could make the system keep using a worse guess forever for that same situation, never trying again for a real answer. Third, we looked at fully rebuilding how a finished automation package gets assembled (removing an old two-copy system), but discovered along the way that a real screen in the Build Studio — the one that lets a builder browse a compiled package's files — depends on exactly the files that rewrite would have deleted. So instead of a risky rebuild, we fixed the actual problem: a handful of spots that would quietly ship a package missing pieces (like its drift-detection fingerprint or a linked backup automation) if one of its files got corrupted moments after being written, instead of stopping and saying so. Finally, several places that manage saved automations, groups, and settings will now speak up with a clear warning if a saved file turns out to be corrupted, rather than quietly acting as if that item never existed. Several other spots that looked like bugs during this work turned out, on closer inspection, to be intentional and already correct — those were left alone rather than "fixed" into something worse.

## Cleaned out old leftover code from the automation compiler and made several silent failures speak up — 2026-09-14
The part of the system that turns a recording into a working automation had built up old, unused code over time — like a garage full of tools nobody uses because the job they were bought for doesn't exist anymore. Some of it was harmless clutter (about 250 lines removed with no change in behavior, all double-checked against the full test suite before and after). But one piece was an active problem: a leftover step from an old version of the system was still running every time someone renamed an automation package or one of its automations, and it would quietly overwrite that package's correct instructions file with an outdated one describing a completely different, no-longer-used way of running automations — a customer or teammate opening those instructions after a rename would have been told to do something that doesn't apply anymore. That's now removed. Separately, several places that should have raised a clear error when something went wrong — a missing software component, a corrupted settings file, a corrupted automation-pack file — were instead quietly working around the problem and continuing on with a degraded result, with nothing to indicate anything was wrong. Those spots now fail loudly and say exactly what broke, so a real problem gets noticed and fixed immediately instead of surfacing later as a confusing, hard-to-trace symptom. This is the first half of a larger cleanup; the remaining, riskier half (a bigger rewrite of how the finished automation package gets assembled) is written down as future work, not yet started.

## Planned: the compiler will ask a few quick questions instead of silently guessing — 2026-09-13
When a recording is turned into an automation, the system quietly guesses things only the person who recorded it really knows — like whether a typed name should be the same every time, or whether an uploaded file should change on each run. A wrong guess about a file upload is especially bad: the file sits on the recorder's computer, so the automation breaks for every customer. The plan is for the review screen to show a handful of simple multiple-choice questions, only when the system is genuinely unsure, and never stop the build to wait for answers. No code changed yet; it is now written down as priority work.

## The reviewer's screen now offers to fix a common recording mistake with one click — 2026-09-13
Automations that download one specific file and upload it somewhere else are extremely common in back-office work, but recording one only ever captures a single example file — the finished automation could only ever handle that one file, not "however many files the customer names." Now, when someone reviews a freshly recorded automation, the screen automatically notices this exact pattern and offers a button: "generalize this to any number of files?" One click rewrites it to ask the customer which files they want, every time it runs. Nothing is guessed by AI here — the system only offers this when it can see, from the recording itself, that the file's name shows up plainly in a web address, so there's no risk of it getting confused. The suggestion never applies itself; a person always has to click Accept, and clicking "no thanks" means it won't ask again for that same automation.

## Fixed a "download from GitHub, upload to Drive" automation that only worked for one specific file — 2026-09-13
An automation recorded once against a single named file (an example ".gitignore" template) could only ever download and upload that exact file, no others — like a copy machine that only photocopies one particular page no matter what you feed it. It now asks which file or files to grab (one, a few, or many, separated by commas), downloads each one in turn, and uploads all of them to Drive together, keeping every file's own name and content intact. Fixing this also uncovered two smaller bugs in how the system decides what questions to ask a user: it was sometimes accidentally turning an already-automatic value (like "whatever file was just downloaded") into a question the user had to answer by hand, and it could ask about a loop's own internal counter as if it were a real setting. Both are fixed, which makes every "repeat this for a list of things" automation more reliable, not just this one.

## Fixed the "generalize to a loop" button producing a loop that downloaded nothing — 2026-09-13
After the previous fix shipped, the reviewer tried it for real: re-recorded the download-and-upload automation, clicked the new "generalize this" button, and ran it — it opened the file's page and did nothing else, over and over, uploading no files at all. The cause was a cleanup step in the recording process that quietly removes clicks it thinks had no effect, using "did the page visibly change?" as its test. A click that starts a file download never visibly changes the page — that's normal, not a sign it's useless — but the cleanup step couldn't tell the difference, so it had deleted the exact click that starts the download. The same blind spot had already deleted a different click (the one that opens the upload picker) in the very first version of this automation, so this wasn't a fluke — it was a rule that would keep breaking things. That rule is now taught to recognize "this click's job is to start a download or open a file picker" and leave those alone. A second, smaller leftover was also cleaned up: a hardcoded click on the one example filename that used to sit outside the new loop, doing nothing useful once the loop visits each file by name directly — the "generalize" button now removes that stray click too, keeping a full record of what it removed in case anyone wants it back.

## Fixed the "generalize to a loop" button not appearing at all for some filenames — 2026-09-13
Right after the previous fix, the reviewer tested again with a different example file — one whose name has a "+" in it — and this time the "generalize this" button didn't show up at all, no error, nothing. The cause: web addresses can't contain certain characters directly, so a browser writes them in a scrambled, encoded form behind the scenes (a "+" becomes "%2B") — like a street address getting typed into a form that only accepts phone-book codes. The system was comparing the plain filename against that scrambled address and never finding a match, so it assumed the pattern it looks for wasn't there. It now un-scrambles the address before comparing, so it correctly recognizes the file no matter what characters are in its name — spaces, symbols, or anything else a browser would encode.

## Uploading a file now always gets double-checked afterward — 2026-09-13
Automations that upload a file used to have no way of noticing if the upload silently failed to register — unlike almost every other step, which checks that something actually happened before moving on. It was like a mail slot with no way to tell if the letter fell in or bounced off the door. Every upload step now confirms the page actually reacted in some way after the file was attached, and stops with a clear error if nothing did, rather than sailing on and only failing much later for a confusing reason. This only applies when no stronger, more specific check already exists for that step — it never adds an extra check on top of one that's already there.

## Stopped taking an unnecessary snapshot when a file gets picked during recording — 2026-09-13
Recording an automation used to take an extra picture of the screen at the exact moment a file was attached to an upload — but the click that opens the file picker, which happens right before, already has its own picture of that same moment. Taking a second, near-identical one was pure waste, like snapping two photos in the same second of the same doorway. That extra picture is no longer taken, which speeds up recording slightly and keeps the file behind the scenes smaller, with no loss of information anyone actually used.

## An automation that downloads files can no longer say "done" while quietly downloading nothing — 2026-09-13
After the last fix, the reviewer tried the whole automation again with real filenames — and it ran without any error message, but nothing actually downloaded. The step responsible for noticing "a file just finished downloading" was designed to simply wait quietly and move on if no download ever showed up, with no complaint at all — like a delivery person who shrugs and drives off if nobody answers the door, instead of leaving a note. That meant an automation could report success while secretly skipping some, or even all, of the files it was supposed to grab. That step now speaks up immediately if a download doesn't happen, stopping the automation right there and saying exactly which file went missing, instead of pressing on silently. A related gap was closed at the same time: if an automation is told to keep going even when one item fails, it now clearly reports how many items it had to skip, instead of only recording that privately for internal diagnostics.
