## Downloaded files now show up in the file-picker window during recording — 2026-08-18
When you recorded a workflow that downloaded a file and then tried to upload it, the file-picker window would open in the right folder but the downloaded file itself was nowhere to be seen — even though it was sitting right there on disk. The window was accidentally set to show only pictures, so documents, spreadsheets, and zip files were hidden. That filter is gone for recording uploads. The picker now shows every file type, opens in the folder where the download actually landed (including inside a zip that was unpacked automatically), and refreshes that folder on Windows before the window appears so nothing is missing.
 — 2026-08-18

## The "Choose File" window now opens in the right folder every time — 2026-08-17
When you record a workflow that downloads a file and then uploads that same file somewhere else, clicking "Choose File" used to open Windows' file-picker window in some unrelated folder, forcing you to hunt around for the file you just downloaded. Three earlier attempts tried to quietly tell Windows' picker to remember the right folder, and none of them held up in practice. This time we took a different approach: Conxa now shows its own file-picker window instead of the operating system's, and opens it already sitting in the exact folder the file landed in. Nothing else about recording an upload changes — you still just click and pick the file — it just always starts in the right place now. This only affects recording; testing or running an already-recorded workflow was never affected by this issue.
 — 2026-08-17

## Logins are now checked before a workflow starts, not in the middle of it — and that's what actually fixed the recording flicker — 2026-08-17
Recording or running a workflow used to sometimes flicker/blink, and separately, if a saved login expired partway through a run, Conxa would try to pop open a sign-in window right in the middle of things. Both of those came from the same bad habit: checking and re-saving login information *during* a recording or a run, instead of only checking it *before* starting. Now Conxa checks every login a workflow actually needs once, right before it starts — if everything's signed in, nothing interrupts you; if something's missing, you're asked to sign in before anything begins, only for the specific app that needs it, not everything in its folder. If a login unexpectedly goes stale mid-run, the run now just stops cleanly and says exactly which app needs attention, instead of surprising you with a pop-up mid-task — you fix it and simply try again. A window rotates its login cookie, or you sign back in by hand while recording — that still gets saved correctly for next time, it just no longer needs constant background checking to do it. (An earlier attempt at fixing the flicker that shipped this same day only slowed down some unrelated background checks and didn't actually fix it — this is the real fix.)
 — 2026-08-17

## When a workflow downloads a zip, it now unpacks it right away — so uploading picks up exactly what you chose — 2026-08-16
Some websites bundle a batch of files into one zip when you download them, but the next website often needs those files uploaded one by one, not as a zip. Before this change, Conxa would guess what you wanted whenever it saw a zip file waiting to be uploaded — it always assumed you wanted the unpacked files, even if you'd actually meant to upload the zip itself. Now Conxa unpacks a downloaded zip immediately, both while you're recording the workflow and while it's running for real — so you can see and choose either the zip or its contents, the same way every time. Whatever you pick during recording is exactly what gets uploaded later: pick the zip, it uploads the zip; pick specific files out of it, it uploads exactly those files. No more guessing on Conxa's part.
 — 2026-08-16

## "Upload all the files I just downloaded" now works even when they're picked all at once — 2026-08-16
Some workflows download a batch of files from one website and then need to hand every single one of them to a second website's upload button — the kind of button where you select many files in one go, not one at a time. Conxa already knew how to hand over a single downloaded file automatically; now it does the same for a whole batch, as long as it can confirm every file in that batch really did come from a download earlier in the same run. If even one file doesn't match up, nothing is guessed — the workflow falls back to asking for the file location the normal way. This closes the last gap in making sure one person's batch of files can never accidentally get sent using a different person's files, even when many files move together.
 — 2026-08-16

## Files you download while recording a workflow now land somewhere you can actually find — 2026-08-17
Before this fix, if you downloaded a file while recording a workflow in the Build Studio, that file didn't go anywhere you could see or find again — it just vanished into a temporary spot the app manages internally. Now every recording gets its own private folder, and anything you download during that recording is saved there with a clear, non-clashing name (so two files with the same name don't overwrite each other). When the next step in your recording is uploading a file, Chromium's own "remember where I was" habit will often open the file picker right in that same folder already — though we can't promise that every time, since browsers don't give any app that level of direct control over their built-in file-picker window. Either way, you now know exactly where to look.
 — 2026-08-17

## The `agent` command now has a reliable fallback on PATH — 2026-08-17
The Cursor agent was installed, but an already-open PowerShell window could not see the updated PATH yet, so typing `agent` failed. A small fallback launcher was added under the user's normal command folder so both `agent` and `cursor-agent` can still find the real Cursor agent install even if a shell only sees that folder. This was tested from PowerShell and Command Prompt, and both now report the Cursor agent version correctly.
 — 2026-08-17

## Cursor, codebase memory, and Ponytail are set up cleanly on this machine — 2026-08-17
The Cursor command-line tools were already installed, but Windows was not resolving all of them cleanly and PATH had an old Cursor location mixed in. The user PATH now points at the real Cursor install, the Cursor agent folder, and the codebase-memory command folder. Clear environment variables were also added so tools can find the exact Cursor CLI, Cursor agent, and codebase-memory MCP program without guessing. Codebase-memory was reinstalled into the supported agent configs, and this repo's graph was refreshed so future code searches can use the knowledge graph again. Ponytail was installed for Codex and copied into Cursor's global rules so both tools get the simple-solution guidance. One small caveat: codebase-memory refreshed the live graph cache successfully, but its optional compressed share artifact did not regenerate even when requested; the working graph itself is fine.
 — 2026-08-17

## A downloaded zip file now automatically unpacks itself before uploading — 2026-08-17
Some websites bundle everything you download into one zip file — click "download all" and you get one package instead of separate documents. But the next website in a workflow often expects to receive those documents one at a time, not as a zip. Before this fix, a workflow would get stuck trying to hand over the zip itself, which the receiving website couldn't use. Now, the moment a workflow needs to upload files that turned out to be inside a zip, it automatically opens the zip first and hands over the actual documents inside — the same way it would if you'd downloaded them separately to begin with. Nothing about how you record or run the workflow changes; this just quietly handles the unpacking in the background.
 — 2026-08-17

## Downloaded files now get their own private, self-cleaning folder for each run — 2026-08-17
When a workflow downloads a file and then uploads it somewhere else, that file now lands in a folder set aside just for that one run, instead of sitting in a shared spot. This means a file from today's run can never get mixed up with a file from an earlier run, and it stays completely separate from anything on your regular computer — your normal Downloads or Documents folders are never touched. The handoff itself already worked automatically (a later step can pick up an earlier download on its own, even when it's uploading to a totally different website), so nothing changes about how that feels to use. What's new is cleanup: these run folders used to pile up forever with no one clearing them out. Now old ones are automatically deleted after a set number of days (a week, by default), so nothing accumulates unnoticed on a customer's machine.
 — 2026-08-17

## A workflow that visits a second website mid-run no longer hits a surprise login screen — 2026-08-16
A workflow could touch two connected websites — say, it starts in one and later clicks through to a second — but we were only checking sign-in for the website it *started* on when deciding whether it was safe to run. Recording worked fine because recording generously signed you into everything up front, which hid the gap. Running the finished workflow on a customer's machine didn't get that same generosity, so it could sail through the first half and then hit a dead login screen it had no plan for, mid-task. Now we track every website a recording actually visits, not just where it begins, and both recording and running check sign-in for all of them — while still signing the workflow into every connected website it might wander into, whether or not that one was required. If several sign-ins have gone stale at once, we now open every needed login window together and say so in one message, instead of making you run the workflow, hit a wall, sign in, run again, hit the next wall, and repeat. And when a mid-run sign-in does expire, we now reopen the login window for the website that actually logged you out — not just the one the workflow happened to start in, which used to sometimes pop open the wrong login screen entirely.
Separately, the "connected" checkmark next to each website in a group's settings used to mean nothing more than "we have a saved sign-in on file for this," even if that sign-in had gone stale days ago — it only got tested right before a recording. Now there's a real "verified" state, and a "Check now" button lets you test a sign-in on demand, per website or for the whole group at once, instead of finding out it's dead the hard way.
 — 2026-08-16

## Recording a workflow no longer quietly logs you out of a saved website — 2026-08-16
Applications are meant to work like a key you cut once: sign in to a website in the Build Studio, and every later recording should just use that saved sign-in without asking again. But recording a workflow was throwing that key away the moment the recording finished — anything the website did to refresh the sign-in while you were working, or a fresh sign-in you typed in because the saved one had gone stale, never got saved back. So the saved sign-in slowly went bad on its own, and eventually you'd be asked to log in again for no obvious reason. Now, the moment a recording stops, whatever the website's sign-in looks like at that point gets saved back to that website, the same way it does today. We also stopped demanding every website in a folder be signed in before you could record a workflow that only uses one of them — recording now only asks for the websites that specific workflow actually visits, matching how running a finished workflow already worked.
 — 2026-08-16

## A workflow no longer waits on logins it doesn't need, just because a groupmate does — 2026-08-16
Workflows are organized into folders (like "Sales"), and each folder can hold several connected websites that need a login. Until now, running any single workflow in a folder demanded that every website in that whole folder be signed in first — even websites that specific workflow never actually visits. So a workflow that had nothing to do with, say, Render, could still get stuck waiting on a Render login window just because it happened to share a folder with a workflow that did use Render. Now, at the moment a workflow is built, we check which of the folder's websites it actually starts on or lands on, and only those are required before it runs. A workflow that doesn't touch a given website is never blocked by it anymore, no matter what else lives in the same folder.
 — 2026-08-16

## Uploading 20 files at once now works — just point the workflow at a folder — 2026-08-16
Picking several files at once in an upload box used to send only the first one, so nineteen out of twenty documents quietly went missing. Now you hand the workflow a folder instead of a file, and it uploads everything inside that folder, in name order. Because it's a single folder location rather than a list of files, the same approach works just as well for two hundred files as for twenty — you never have to hand the files to the assistant one by one, you just tell it where they live. An empty folder now stops with a clear error instead of pretending it uploaded something.
 — 2026-08-16

## Giving a folder to a page that only takes one file now says so plainly — 2026-08-16
Some websites let you attach many files at once; others accept exactly one. The workflow now checks which kind it's looking at, right there on the page, before it tries to attach anything. If you point it at a folder of twenty documents but the page only takes one, it stops immediately and tells you so in those words, instead of failing with a confusing technical message. It also skips its usual round of self-repair attempts in this case — nothing is broken and there is nothing to repair, you simply need to give it a single file. Importantly, it asks the page rather than assuming from how the workflow was originally recorded, so recording with one file and later reusing it for a batch of twenty works exactly as you'd expect.
 — 2026-08-16

## Found that picking 20 files at once to upload only ever sends one of them — 2026-08-16
We wanted practice websites for testing a workflow that moves twenty files at a time, so we checked which free sites let you pick many files in one go and confirmed five that do. Doing that turned up a real limitation in our own product: when someone records themselves selecting several files at once in an upload box, only one of those files survives into the finished workflow. The recording looks completely normal on screen, so nobody would notice until the workflow runs and nineteen documents quietly go missing. It's like handing over a stack of twenty invoices and only the top one making it into the envelope. This is now written up as a priority item to fix, and the testing guide explains how to confirm it in about five minutes.
 — 2026-08-16

## Fixed a new tab pausing for up to two minutes before it typed the web address — 2026-08-16
Right after fixing yesterday's tab mix-up (below), testing turned up a side effect of that very fix: when a workflow opens a brand-new tab itself (like pressing Ctrl+T) and then goes to type a web address into it, the app was sitting there doing nothing for up to a full minute — sometimes two — before it actually entered the address. The cause: a safety wait added to make sure a newly opened tab has actually loaded before acting on it was also being applied to a blank tab the app had just created itself, one that was never going to load anything on its own until the very next step told it exactly where to go. It's like standing at a red light that's stuck on red, waiting for it to turn green, when you were actually supposed to just drive through it because you're the one who's about to move. That wait is now skipped for tabs the app opens itself, and still applied for tabs a website opens on its own (where waiting for it to finish loading is the right thing to do).
 — 2026-08-16

## Fixed a two-tab workflow replaying on the wrong page and giving up too soon on slow websites — 2026-08-16
A workflow that logs into Render and then opens a Vercel project in a new tab was failing on replay. Two separate problems were combining. First, the app only waited 15 seconds for a page to finish loading before moving on — not long enough for a slower site like Vercel, so it would try to click things that hadn't appeared yet. That wait has been raised to a full minute everywhere it matters, like giving someone more time to answer the door before assuming nobody's home. Second, and more seriously, when a workflow opens more than one browser tab, the app could lose track of which tab it should be typing into — it would end up filling in a login form on the wrong tab entirely, the one that was supposed to stay untouched. That mix-up is now prevented: the app keeps a clear record of which tab it has already assigned to which step, so a tab that's already spoken for can never be handed out again by mistake. A related recording bug that could occasionally mislabel which tab a popup came from was fixed too, so newly recorded workflows won't repeat the problem.
 — 2026-08-16
