Conxa · runtime sign-in

The Login Desk

When a customer signs in through Conxa, how do we know they're done, so we can save the login and close the window ourselves? And how do we do it when the only thing we're given is the login address?

Each app gives us: ✓ login address target address

The target page is often a completely different website, changes over time, or depends on the account. So nothing on this page relies on it.

Where we are

Today we guess from the address bar

Every 1.5 seconds we look at the web address. Once it stops looking like a login page, we assume the sign-in worked, wait 1.5 seconds, save and close. It's like guessing someone checked in because you saw them walk past reception. Usually right, but pop-up logins, texted codes and slow sites all fool it.

The key trick

Ask for the login page again

Most websites send a logged-in person straight past their own login page. Open /login while already signed in, and you get bounced to your dashboard. So we don't need to know where the app lives. We just ask for the login address twice, once before and once after, and compare.

Finding the app without being told

Follow the journey, skip the sign-in services

We record every website the login tab visits. Well-known sign-in services (Google, Microsoft, Okta, Auth0, Apple, GitHub's sign-in pages) never count as "arrived". The first stop after the login page and those services is the app, even if it's a completely different website from the login address.

The cast

Who works at the desk

Each part has exactly one job. Lookouts only raise their hand. Only the judge (or, as a last resort, the customer) can say "logged in". Only the timekeeper can save.

Lookouts · "something happened"
  • Journey: left the login page and the sign-in services
  • Password box: was on screen, now gone from every tab and frame
  • Tickets: new login cookies, or a new token in the page's memory

All three work on any website, in any language, from day one.

Pause sign · "not finished yet"

Spots screens that mean the sign-in is still going: a short box for a texted code, "choose an account", "approve on your phone", "trust this device?", a CAPTCHA. It reads how the page is built, not its words. While it's up, lookouts don't count.

Judge · "is this person logged in?"

Asks for the login address again in the background, with the window's tickets, and compares it with the "before" snapshot. Only asks when a lookout raises a hand, so the site doesn't get suspicious.

Timekeeper · "is it calm?"

After a yes, checks every half second whether the tickets are still changing. Same twice in a row means save. Still changing after 5 seconds means save anyway, because some sites never go quiet.

Prover · "does the save work?"

Right after saving, tries the saved login in a fresh background check. If it doesn't work, the customer is told now, not on their next run.

The customer · last resort

If the signals are still unclear after about 25 seconds, Conxa Execute's own panel shows an "I'm done signing in" button. It's never injected into the website, and nobody gets stuck.

Step 1 of 2 · once

What happens during recording

Everything above runs on a customer's machine, every time. But it only has a login address to work with because someone typed one in first. That happens once, ahead of time, inside Build Studio — the tool the company (not the customer) uses to build the skill.

A person on the company's team opens the app's settings and fills in two boxes: a name (say, "Salesforce") and a login address — where the sign-in page lives. A third box, Success URL, is marked optional on purpose, because the page you land on after signing in is often unpredictable: a different website entirely, a page that depends on the account, or one that changes when the app is redesigned. Most teams leave it blank, which is exactly the situation this whole design is built to handle well.

This is a lighter cousin of everything on this page: recording only needs two of the simplest checks, because a technical person is sitting right there and can notice if something looks wrong. Runtime can't lean on that — a customer isn't watching for a warning message, so it needs the fuller set of checks described below.

Step 2 of 2 · every time

What happens at runtime

Every time a customer runs a skill that needs this app, their copy of Conxa reads back exactly one thing from the recording above: the login address. It has no idea what the destination page looks like, and it doesn't need to.

In detail, moment by moment:

  1. 1Runtime quietly loads the login address in the background — the "before" snapshot. If it already bounces to somewhere that isn't a login form, an old saved login still works: it saves at once and the customer barely sees a window.
  2. 2Otherwise it opens a real, visible window at the login address, and the customer signs in exactly as they would anywhere else.
  3. 3The pause sign watches for a mid-sign-in screen (a texted code, "choose an account"). While it's up, nothing below counts yet.
  4. 4The three lookouts — journey, password box, tickets — watch for any sign the sign-in finished, on any website the sign-in leads to, not just the one typed in during recording.
  5. 5The judge asks the login address again in the background and compares it with step 1's snapshot. This is the one check that doesn't need a target address at all.
  6. 6The timekeeper waits for the tickets to stop changing, the prover checks the save actually works, and only then does the window close on its own.

    Rules we keep

    Safety

    Secrets stay on the machine

    We only ever note ticket names and page shapes. Ticket values and passwords are never logged or sent anywhere.

    Gentle with the website

    The judge asks only when a lookout fires, never on a timer, so the site's bot protection isn't provoked.

    Only this login's tabs

    In Conxa Execute, lookouts watch only the tabs this login opened, never another app's login happening at the same time.

    We never touch the website

    The "I'm done" button lives in Conxa's own panel. Nothing is injected into the site's page.

    How we'd build it

    Two phases

    Phase 1 · runtime only

    Everything that needs only the login address

    • The judge: before/after login-page check
    • Journey tracking with the sign-in services list
    • Password-box watch across tabs and frames
    • Ticket watch: cookies and page memory
    • Pause sign for mid-sign-in screens
    • Timekeeper, then save, then prove
    • Instant close when an old login still works
    • Remember the landing address for pre-run checks
    Phase 2 · polish

    For the sites that still misbehave

    • "I'm done signing in" button in Conxa Execute
    • A log of which signal decided (never any values), to tune on real logins
    • "Signed in as ___" confirmation
    • Optional per-site fingerprint from the Build Studio, only if Phase 1 falls short
    In one sentence

    Lookouts notice, the website confirms by bouncing us off its own login page, we wait for calm, save, and prove the save works. All from nothing but the login address.
