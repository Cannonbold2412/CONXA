Distribution & update architecture

Conxa Distribution Map

Five separate things ship to five separate places on five separate clocks. This is what each one is, who pushes it, and exactly how a new version reaches a customer's laptop — in plain language.

The shape of it

Three owners, one direction of travel

Nothing in Conxa runs "in the cloud" the way people usually mean. A SaaS company records and compiles workflows on its own Windows machine. The cloud stores the result and hands it out. The customer's own laptop runs it. Work only ever flows left to right.

Why this matters

Because execution never touches Conxa's servers, an outage on Conxa's side cannot stop a customer's automation from running. The worst a cloud outage does is delay an update. Everything on disk keeps working from its last-known-good copy.

Inventory

The five shippable artifacts

People assume "the product" is one download. It is five, and they update independently on purpose — so a two-line fix to a skill does not require anyone to reinstall an 85 MB program.

acme.com-Agent-Setup.exe
built in Studio

The company-branded installer the end customer double-clicks. Named after the company's own domain. Built once; almost never rebuilt.

conxa-runtime.exe  (host layer)
cloud-updated

The heavy engine: Node, Playwright, all the libraries. Roughly 85 MB. Changes a few times a year. This is the file every AI agent app is pointed at.

conxa-app  (app layer)
cloud-updated

The actual logic — step executor, element resolver, recovery, sync. About 60 KB zipped. Changes every release. This is where virtually all improvement ships.

skill packs
cloud-updated

A handful of small data files per workflow. One skill can be updated without touching any other skill.

Conxa Execute & Build Studio
desktop apps

Two ordinary Electron desktop apps with ordinary self-updaters. Studio is for the company that builds skills; Execute is a chat app for whoever runs them.

The split that does the work

Splitting the runtime into a big, rarely-changing engine and a tiny, frequently-changing logic layer is the single most important decision in this whole design. It means shipping a fix is a 60 KB download that lands the same second the app opens — not an 85 MB re-download and not a reinstall.

The surprise

The installer contains almost nothing

You would expect a company's installer to carry that company's skills inside it. It deliberately doesn't. The installer ships the engine, the logic layer, and one small text file — pack.json — which holds the company's identity, the address to phone home to, and two tokens: one to download skills, one to report usage.

Zero skill files are inside the .exe. The runtime downloads all of them on its very first run, using exactly the same code path it will use for every update afterward.

That is a deliberate trade. It means there is only ever one way skills land on disk, so the "first install" case can't silently drift out of sync with the "routine update" case. It also means an installer built months ago still delivers today's skills — because it was never carrying yesterday's.

The guard rail

The build refuses to produce an installer whose pack.json has no sync token — i.e. one whose skills were never published. You cannot accidentally ship a customer an installer that phones home to nowhere.

Install day

What happens in the ninety seconds after the double-click

This is a genuine sequence — each step depends on the one before it — so it is worth reading in order. The whole thing is a per-user install: no administrator password, no system-wide changes.

  1. Files land in the user's home folder

    The engine, the logic layer, and pack.json are written under ~/.conxa. Nothing goes into Program Files, nothing needs elevation.

  2. A private browser is downloaded

    The installer asks the engine to fetch its own copy of Chromium. Conxa never drives the customer's personal Chrome, so their own browsing, profiles and extensions are untouched.

  3. First sync pulls every skill down

    The engine calls the cloud with its sync token and receives the company's skills. Each file is checksum-verified and written atomically — write to a temporary name, verify, then rename into place. If anything fails halfway, the previous state is restored rather than left half-written.

    Each skill lands in its own versioned folder with a pointer marking which version is active. That pointer is the mechanism that makes instant rollback possible later.

  4. Every AI agent app on the machine is registered

    The engine detects which agent apps are installed — Claude Desktop, Claude Code, Cursor, VS Code, Windsurf, Codex, Zed, Copilot CLI and about a dozen more — and adds itself to each one's configuration. Comments and formatting in those files are preserved, writes are atomic, and it will never overwrite an entry that isn't its own.

  5. Each agent app is told what the skills do

    A short instructions file is dropped into each registered app so the AI actually knows these tools exist and reaches for them. This happens after the sync, not before — there's nothing to describe until the skills have arrived.

  6. The installer reports honestly

    A status line is written and shown in the final dialog — for example "15 ok, 3 not installed, 1 left alone, 1 FAILED". This exists because the installer's exit code only fails if every app failed; without the status line, 14 successes and 1 failure would have shown a cheerful "Setup complete!".

The core mechanism

Four update clocks, running at different speeds

This table is the heart of the whole design. Each artifact has its own trigger and its own moment of taking effect — and the differences are not accidents, they follow from physics.

ArtifactSizeChecked whenTakes effect
App layer (logic) ~60 KB Every launch, before the logic loads The same launch — instantly
Host engine ~85 MB Every launch, just after startup Next time the app is reopened
Skills a few KB Every launch (skipped if synced <5 min ago) Immediately after download
Conxa Execute / Build Studio ~100 MB On app start On quit & relaunch

Why the logic layer lands instantly but the engine can't

The logic-layer check runs before the program has loaded any of its own code. Nothing is in memory yet, so swapping the files on disk and then loading them is completely safe — the update is live for the very launch that downloaded it. The download budget is deliberately tight (a three-second check, two short retries for the zip), because every millisecond here is a millisecond the user waits. Any failure at all — no network, bad signature, corrupt zip — is quietly swallowed and the program carries on with whatever it already had.

The engine is a different problem: a running program cannot overwrite its own executable file while it is running. So the new engine is downloaded into a separate folder, never touching the file the current process is executing from. Before it is made active, the new engine is launched once in self-check mode and must exit cleanly. A matching checksum only proves the download wasn't corrupted; it doesn't prove the program actually starts. If the self-check fails, the update is abandoned and the old, known-good engine stays active.

Because the new engine only takes over on the next cold start, the runtime politely refuses to begin new automation runs while an engine update is staged — telling the user to quit and reopen their AI app to finish. Scheduled background runs are exempt, and the block releases itself after three launches that never picked the update up, so nobody can get permanently stuck.

The gatekeeper

One signed file decides everything

There is no collection of update endpoints. There is a single manifest the runtime fetches fresh on every launch, listing the current version of every component plus its checksum. It is cryptographically signed by the cloud, and the runtime verifies that signature against a public key baked into the engine at build time.

A manifest that fails verification isn't partially trusted or retried — it's discarded exactly as if the network had been down. That is the whole defence against someone impersonating the update server: a forged manifest simply doesn't exist as far as the runtime is concerned.

Once verified, five independent gates decide whether any given component actually updates:

01

Is it actually newer? A plain version comparison. Same or older is ignored.

02

Will the engine still run it? Each logic-layer version declares the oldest engine it can run on. If the machine's engine is older than that, the update is refused outright — rather than installed, crashed, and rolled back on every single launch.

03

Is this machine in the rollout? A share of machines can be let in first. The answer is computed from the machine's own install ID, so it's stable — a machine that's "out" at 20% stays out until the percentage rises, rather than flip-flopping on every check.

04

Is there a hard floor? A minimum version can be set that overrides the staged rollout entirely. This is the emergency lever for a security fix: everybody, now.

05

Does the downloaded file match? Checksums are verified on every artifact, every time, before anything is activated.

Operational note

If the cloud is misconfigured and loses its signing key, it would serve an unsigned manifest — which every runtime would then correctly discard, silently halting updates everywhere with no error visible on either side. So the cloud now refuses to start at all without its signing key. A loud failure at deploy time beats a silent one in the field.

The human gate

Publishing is not deploying

When a company publishes a skill from the Build Studio, nothing reaches a single customer. Publishing writes a permanent, immutable snapshot of that version and marks it ready. That's it. The live pointer doesn't move, the manifest doesn't change, and the sync endpoint still hands out the previous version.

A separate, deliberate action by a Conxa administrator — Release — is what makes it live. A version can sit ready for five minutes or five weeks; there is no timer and no auto-promotion.

ready

Published and permanently stored. Reviewable, diffable, testable. Invisible to every customer.

published

Released. The live pointer has moved; the next machine to sync gets it.

superseded

A newer version took the pointer. The old snapshot is untouched and still on disk — which is what makes rollback instant.

failed release

Something broke mid-release. The live pointer never moved, so customers saw nothing. The version stays ready and the release can simply be retried — no republish needed.

Why the ordering is the safety property

Inside a release, every step that could plausibly fail — writing files, updating records — happens before the live pointer moves. Moving the pointer is the very last act. So a half-finished release is always invisible rather than half-visible. There is no such thing as a customer receiving a partially-released skill.

Rollback is the same machinery with the steps that create things removed: it takes an older snapshot that already exists and moves the pointer back. Nothing is rebuilt, nothing is re-uploaded, nothing is recompiled. And it is always scoped to one workflow — there is no way to roll back a whole group by accident.

Failure design

Every update can be undone without a download

The engine, the logic layer, and each individual skill all use the same on-disk trick. Each version lives in its own folder, and a pointer marks which one is active. Updating means writing a new folder and then moving the pointer. Rolling back means moving the pointer back — no network involved.

Old versions are kept (current plus two previous by default), and the version that was live immediately before an update is explicitly protected from cleanup. That is what guarantees a rollback in the same session never needs to re-download anything.

If the logic layer fails to load on startup, the program rolls the pointer back itself and retries, automatically, before the user sees anything. If a skill's files fail their checksum mid-sync, the previous folder is restored and the failure is recorded so the dashboard can show that deployment as failed — an entry that clears itself the moment that skill next updates successfully.

The pattern, stated once

Download somewhere new. Verify it. Prove it runs. Then move the pointer. Keep the old copy. Every update path in Conxa is a variation on those five moves.

Where Execute sits

Conxa Execute is a client, not a channel

Conxa Execute is a desktop chat app for people who want to run skills without wiring up Claude Desktop. It is important to be precise about what it is not: it is not a distribution channel, it does not carry skills, and it does not carry a runtime.

It looks for the engine the company installer already put on disk, at exactly the same location every AI agent app was pointed at, and talks to it the same way Claude Desktop does. If the installer was never run, Execute has nothing to drive. It is one more front door onto the same installation, alongside Claude Desktop, Cursor, and the background scheduler.

Execute's one genuine difference is cosmetic and local: when it drives a visible run, the browser appears in a panel inside Execute's own window instead of opening a separate Chromium window. Every other agent app takes the ordinary path — not because the runtime checks who's calling, but because only Execute passes the flag that switches it on.

Execute updates itself like any normal desktop app: it checks a feed on the cloud at startup, downloads in the background, and installs on quit. That is a completely separate clock from everything above.

Common confusion

"Installing Conxa Execute" and "installing the company's agent" are two different acts. The company installer delivers the engine and the skills; Execute is an optional nicer way to talk to them. Uninstalling Execute leaves every skill and every other agent app registration intact.

Identity & trust

Who is allowed to ask for what

Three different credentials cover three different jobs, and they're deliberately separate so a leak of one doesn't cascade.

CredentialHeld byCan doIf leaked
Company loginThe SaaS company's staff Record, compile, publish, build installers Normal account compromise — but it still cannot release anything live
Sync tokenBaked into each installer Download that one company's skills, read-only Read access to skill definitions; rotatable by re-minting
Tracking tokenBaked into each installer Report usage events for that company Noise in telemetry; no read access to anything

The end customer never has a Conxa account and never logs in. They only ever log into their own target platform — and when they do, that browser session is encrypted on disk with a key unique to their machine, held in their operating system's keychain.

That last detail is the point of the whole separation: someone who obtains a company's installer gets the sync token, and with it the ability to read that company's skill definitions. They still cannot decrypt a single customer's saved login session, because the key for that never left the customer's machine and was never in the installer to begin with.

Two parallel worlds

Dev and production never touch

A single switch selects one of two completely isolated stacks that can coexist on one machine. Different install folders, different data folders, different cloud addresses, different update channels — and a different registration key in every agent app's config, so a development install and a production install appear as two distinct entries that can never be mistaken for one another.

The defaults deliberately point in opposite directions on either side. A shipped customer install with nothing configured defaults to production — because the dangerous mistake on a customer machine is quietly using the development stack. A developer's workstation with nothing configured defaults to development — because the dangerous mistake there is accidentally touching production.

The cloud address a skill pack phones home to is frozen into it at publish time, not decided at runtime. An installer built against development can therefore never reach production, no matter how it is later configured.

Summary

The whole thing in six sentences

A company records and compiles workflows entirely on its own machine and publishes them to Conxa Cloud, where they sit as immutable, reviewed snapshots until an administrator releases them. Customers install one thin, company-branded program that contains the engine, the logic layer, and a single configuration file — no skills at all.

On first run that program downloads the skills itself, registers itself with every AI agent app on the machine, and tells each one what the skills do. From then on, every launch fetches one cryptographically signed manifest and independently decides whether to update the logic layer, the engine, and each individual skill — each on its own clock and each behind its own compatibility, rollout and checksum gates.

The tiny logic layer updates before it loads and is therefore live the same second; the heavy engine stages itself in a fresh folder, proves it boots, and takes over on the next launch. Everything can be undone by moving a pointer back, and nothing runs on Conxa's servers at any point.
