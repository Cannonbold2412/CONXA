# Fix Log — 2026-07-15

## Fixed the recorder silently cutting off a HubSpot workflow recording mid-session — 2026-07-15

Investigated a report of a "Create a Contact in HubSpot" recording that only kept the first 5 clicks
— everything the user did after clicking "Create new" (filling out the actual contact form) never
showed up, in the recording OR the compiled skill.

Pulled the raw evidence for that exact recording: only 6 actions were ever written to disk, and the
recording's own internal activity log goes completely silent within a fraction of a second of that
last click. But the video file recorded alongside it tells a different story — decoding it shows the
browser kept rendering real content for another 7+ seconds after that, and the video file itself was
cut off mid-write rather than closed out properly. Put together, this proves the browser was still
open and the user was still actively working in it — the recorder just gave up and quietly ended the
session early, thinking the browser had closed when it hadn't. So this wasn't the earlier iframe
dedup bug (nothing was collapsed or dropped afterward) — the recording itself stopped listening while
the user kept going.

The recorder checks, several times a second, whether any browser tab is still open, and the instant
it sees none, it treats that as "the user is done, wrap up now." The problem: that check can come back
empty for a brief moment even while the browser is still open — for example, right as a single-page
app like HubSpot swaps out its page during a heavier action like opening a "Create new" panel. A
single bad reading was enough to end the whole recording immediately and permanently, with no way to
tell that from someone genuinely closing the browser.

First fix attempt gave that check a short (2 second) grace period before giving up, instead of
trusting the very first blip. The user re-recorded the same workflow to test it — same exact failure,
same exact spot. That re-record was actually useful evidence: it showed the recorder's bridge
successfully loaded into HubSpot's "create contact" panel (a known-heavy embedded form) moments after
the "Create new" click, then everything went silent anyway. So the empty reading wasn't a quick blink,
it was a real multi-second stall while that heavy panel loaded — longer than the first fix's 2-second
patience. Widened the grace period to about 8 seconds and applied it evenly to both signals the
recorder uses to decide "the browser is gone" (not just one of them, in case either one was the one
actually flickering). A real, intentional browser close is unaffected — it just confirms a few seconds
later than before, which nobody will notice — while a slow in-app panel load now gets ridden out
instead of silently killing the recording. Still needs a live re-record to fully confirm.

## Fixed "Record Workflow" popup getting permanently stuck after recording — 2026-07-15

A user recorded a workflow, closed the browser like the instructions say, and the "Record Workflow"
popup just sat there forever saying "Browser is open — perform your workflow, then close it when
done." — even though the browser really was closed. The X button did nothing either, so there was
no way out except force-quitting the app.

The popup is designed to notice the browser closing on its own and automatically move on to saving
— it checks in with the background process once a second waiting for that signal, and the X button
is deliberately blocked from closing early so a recording in progress can't be lost by an accidental
click. The problem: if that one automatic signal is ever missed or delayed for any reason, the user
had absolutely no other way forward. No "I'm done, save it now" button, no cancel button — total
dead end.

The sibling "Record Login" popup already solves exactly this with two backup buttons: "Save Session
Now" (finish immediately, don't wait for the auto-detection) and "Cancel" (back out of the recording
entirely). The Workflow popup never got the same treatment. Fixed by adding the same two buttons —
"Save Workflow Now" and "Cancel" — to the Workflow recording popup, so it's never a dead end again
regardless of whether the automatic detection works.

## Fixed the compile/recompile screen looking frozen during "Generate selectors" — 2026-07-15

A user reported that clicking Compile gets stuck on the "Generate selectors" step: the log stops
printing new lines, the "API calls" list stays empty, and the little timer next to that step just
shows "…" forever. Since this screen exists specifically to reassure people that compiling is
still happening, a screen that looks dead is worse than no screen at all — even if the work is
actually still going on in the background.

Turned out the compiler already narrates its own progress in detail — "Compiling step 3", "Generating
vision anchors for step 3", "Compiled step 3" and so on — but that narration was being thrown away
before it ever reached the screen, because Build Studio never plugged in the wiring needed to
forward it. So during a phase that can legitimately take over a minute (each step needs its own
round trip to the AI service), the user was left staring at a screen with nothing changing, unable
to tell "still working" apart from "actually broken."

Fixed by connecting that existing narration to the screen, so the compile log now fills in
continuously step by step instead of going silent for the whole "Generate selectors" phase. Also
made the little timer next to the running step count up live (1s, 2s, 3s...) instead of sitting on a
static "…", so even a naturally quiet moment still visibly shows time passing. Verified the
timer ticks and the log streams during a real compile, and that failures (e.g. losing internet
mid-compile) still show the same error message as before.

## Fixed recorded steps inside iframes silently disappearing at compile time (e.g. HubSpot workflows) — 2026-07-15

A user recorded a 30+ step workflow in HubSpot that included actions inside iframes (embedded
widgets HubSpot uses for things like the contact editor, forms, and note composer). After closing
the browser, the "Save Recording" dialog sat there for a long time, so the user closed and reopened
Build Studio and compiled anyway. The compiled workflow only had 7 steps — every action recorded
inside an iframe was gone.

Investigated the full path a recording takes — capture, save, disk storage, and compilation — to
find where the steps actually went missing, rather than just working around this one recording.
The recording and saving were fine: all 30+ steps were safely written to disk the whole time, and
the "stuck" dialog was a separate, unrelated slowness issue (extracting preview screenshots for
every step one at a time can take a while for a long recording — not a data-loss problem).

The real bug was in compilation. Before turning raw recorded actions into a finished workflow, the
compiler cleans up near-duplicate steps — for example, if you click into a text box and then type
into it, it collapses that into one "type" step instead of two. To decide whether two steps are
"the same field," it built a fingerprint from things like the field's name, id, and label. But that
fingerprint never took into account *which iframe* the field was in. HubSpot's embedded widgets
often reuse generic, unlabeled fields (no name, no id, no label) across several different iframes,
so many genuinely different fields fingerprinted identically. The cleanup logic saw what looked
like the same field being typed into over and over and collapsed all of them down to the last one
recorded — that's exactly how 30+ steps shrank to 7, and worse, it could even keep the wrong value
attached to the wrong step.

Fixed by making that fingerprint include which iframe (or none) each step happened in, so fields
that only look alike but live in different iframes are never treated as the same field. Verified
with a synthetic HubSpot-style recording (several iframes, generic fields, no real labels) run
through the actual save-and-compile path: before the fix, 3 distinct iframe steps collapsed into 1;
after the fix, all 3 compile through correctly with no regressions to the legitimate case (retyping
into the same field, in the same iframe, still collapses to one step, exactly as before).
