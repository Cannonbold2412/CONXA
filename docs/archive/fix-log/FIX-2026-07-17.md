# Fix Log — 2026-07-17

## Made the runtime actually handle steps that live inside a panel, not just record and show them — 2026-07-17

After yesterday's fix made steps inside an embedded panel (like HubSpot's Create Contact form)
record, save, and display correctly, the next question was: can the automation actually replay one
of those steps, and if it fails, can the self-healing recovery fix it? Checked carefully, and the
answer was no, in five separate ways.

The self-healing recovery's "here's what's on the page right now" summary, sent to the automation
whenever a step fails, was built by looking only at the outer page — never inside any panel. So a
step that failed inside a panel got a summary that simply didn't mention anything in that panel,
including the very thing the recovery was supposed to find. Fixed by also gathering that same kind
of summary from inside the panel when relevant, and telling the recovery explicitly "this step's
target lives inside a panel" so it isn't left guessing.

Separately, the automatic checks that confirm a step actually worked (e.g. "did this field now show
the right value") were also only ever looking at the outer page, so a check for something inside a
panel would always report failure even when the step worked perfectly. Fixed so these checks look
in the same place the step itself acted.

A smaller one: a fallback that scrolls a stuck element into view was also only looking at the outer
page. Fixed to scroll inside the right panel instead.

Also added: if a panel that's supposed to contain a step's target can't be found at all — closed, or
changed in a way that broke its own tracking marker — that's now reported honestly ("the panel
itself couldn't be found") instead of being silently treated as if it were still the same panel and
searched in the wrong place, which could have caused the wrong thing to be clicked entirely by
accident. And if a workflow was ever recorded with a broken/incomplete panel reference, that now
shows up as a visible warning instead of failing silently later.

Verified against a real, running browser with a real nested panel (not just simulated data): a step
correctly acts on the field inside the panel and not a similarly-named one outside it; a step whose
panel genuinely doesn't exist is now reported honestly instead of accidentally acting on the wrong
part of the page; the "what's on the page" summary and the pass/fail checks both correctly see
inside the panel. Full test suite (both the automation side and the recording/compiling side)
passes clean, no regressions.
