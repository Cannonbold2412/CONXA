# Fix Log — 2026-09-24

## Found the real reason GitHub sign-ins kept failing, and fixed it properly instead of patching around it — 2026-09-24
The GitHub-to-Drive workflow's saved GitHub sign-in kept failing its "are you still signed in" check, even though the sign-in itself was perfectly valid — this is the third issue noted in yesterday's entry below. The real cause was two separate mistakes, both in how the system recognized a website by its address. First, GitHub's sign-in page address has a "www." at the front, but GitHub itself drops the "www." once you're signed in — so the check was comparing "www.github.com" against "github.com" and never finding a match, like a security guard checking a badge against "Robert Smith" when the badge says "Bob Smith." Second, and more importantly, the system had a fixed list of "these are sign-in services, not the actual app" (Google, Microsoft, and others) that included GitHub by name — which is wrong, because for this workflow GitHub *is* the app someone is signing into, not a middleman fronting some other app. That mistake meant the system could never recognize a finished GitHub sign-in at all. Rather than just patching those two specific spots — which would only wait for the next website with a similar quirk to break the same way — the whole recognition method was replaced. It now checks a website's actual sign-in page twice: once with no sign-in information at all, to see honestly what "signed out" looks like, and once with the saved sign-in, to see if the page looks different and no longer shows a sign-in form. That comparison works for any website, with no fixed lists or address-matching tricks to go stale. Along the way, two related timing bugs were found and fixed where a sign-in that finished very quickly, or in a different browser tab than the one that opened, could be missed entirely.

## Found and fixed a second sign-in problem in the GitHub-to-Drive workflow, and found a third one still open — 2026-09-24
After yesterday's fix, testing this workflow again still failed, but for a new reason: once the system correctly noticed it needed a saved sign-in, it checked whether that sign-in was still good by visiting the app's sign-in page directly — and for GitHub, the address it checked ("www.github.com") didn't quite match the address the browser actually lands on when you're signed in ("github.com," no "www"). Like a receptionist checking a guest list against "Robert" when the name on file says "Bob" — same person, technically different spelling, so the guest gets turned away. Setting the correct "you're signed in" address for both Google and GitHub fixed this. A third, smaller issue turned up while testing: GitHub's sign-in check still fails sometimes when it runs alongside Google's check in the same browser window, even though the saved sign-in is genuinely valid — that one is written down to investigate further but does not affect the two fixes above.

## Fixed a workflow forgetting to bring its saved sign-in along when a related app used a slightly different address — 2026-09-24
A workflow that hands off a file from GitHub to Google Drive was landing on Google's public "please sign in" page during testing, even though a valid Google sign-in was already saved for that team. The cause: the system checks which saved sign-ins a workflow will need by comparing web addresses, but it was comparing them too strictly — it didn't recognize that "drive.google.com" and the saved sign-in's address "accounts.google.com" belong to the same Google account. Because of that mismatch, the workflow was quietly marked as needing no sign-in at all, so its browser never picked up the saved one. It's like a hotel key card being rejected at a side door because the record only listed the front door's address — even though it's the same building. The comparison now recognizes addresses on the same site as covering each other, matching a check elsewhere in the system that already worked this way.

## The compiler can now clean up an obviously duplicated "go to this page" step — 2026-09-24
When a recording opened a new browser tab and the very next thing it did was load a page, the compiler sometimes ended up writing that same page-load down twice in a row — the reviewer's AI check would even notice and label the second one "redundant," but had no way to actually remove it. Now that AI check is allowed to flag exactly this one situation: two back-to-back "go to" steps pointing at the identical page in the identical tab. It still double-checks the AI's flag against the actual recording before acting, and the removed step is archived rather than deleted, so nothing is ever lost for good.

## You can now archive a published workflow from Skill Packages — 2026-09-24
Skill Packages now has an Archive button on each workflow's page. Archiving a workflow makes it disappear from every customer's AI assistant — it stops showing up in their skill list and can no longer be run — while leaving the actual files already on their computers untouched, and keeping the workflow's full release history intact. A Restore button brings it right back with nothing lost, since nothing was ever deleted. Think of it like unplugging a light switch rather than tearing out the wiring: the workflow goes dark everywhere immediately, but reconnecting it is instant. This gives teams a safe way to retire a workflow without permanently losing it.

## Fixed the login window closing itself before you could sign in — 2026-09-24
Connecting some apps (GitHub was the one reported) opened the sign-in window and then closed it again after about a second, before anyone had a chance to type a password. This happened because many sites bounce you to a slightly different address the instant their login page loads, and the app was mistaking that automatic bounce for "you're done signing in." Now it only closes on its own when it detects the real signed-in page, or when you close it yourself — so you get a real chance to sign in. If you hit this with GitHub specifically, also set its Success URL to `https://github.com/` so the window can still close by itself once you're actually signed in.
