## Taught the assistant to notice and clear away surprise pop-ups during a run — 2026-09-03
Sometimes a website shows a pop-up nobody recorded — a "20% off!" banner, a permission prompt, a one-off cookie box our known-pattern list doesn't recognize. Until now, if the built-in cleanup couldn't recognize it, the run just failed with a plain "couldn't find the button" message, leaving the person to figure out on their own that a random pop-up was actually the problem. Now, when that happens, the assistant is told outright "something unexpected is covering the page" and shown exactly what's on it, so it can close the pop-up itself and carry on with the task. It's on a short leash for safety: it's only ever allowed to press something that reads like Close, Cancel, or Skip — never Accept, Confirm, Delete, or Buy, so it can never accidentally agree to something or click a real button dressed up as a pop-up. And once it figures out how to close a particular pop-up on a particular site, it remembers, so the same pop-up doesn't cost time or money to clear a second time.

## Explained why the recorder pops up its own box for browser alerts instead of the browser's own box — 2026-09-03
No code change — a documentation question came up while reviewing the still-open pop-up test. When a website tries to show one of the plain grey pop-up boxes browsers use to ask "are you sure?" or "type something," Conxa shows its own window instead of letting the real one appear. This is not a shortcut we could remove — the moment Conxa is watching a page closely enough to record it, the browser itself refuses to draw its own pop-up at all, and it also never tells Conxa what a person typed into one unless Conxa is the one who answered it. So showing our own window is the only way to actually capture what someone meant to click or type, and skipping it would make every recorded pop-up step blank instead of correct. Wrote this up as a shareable page with diagrams and a worked example. Also confirmed this is unrelated to the pop-up test still failing during playback — that's a separate, already-tracked timing issue on the playback side, not the recording box.

## Fixed a "you have to answer this pop-up twice" bug during recording — 2026-09-03
When a website shows a pop-up asking "are you sure?" or "type something," Conxa's own window appears so a person can answer it while recording. But sometimes that window would get stuck on top of the browser and never go away by itself, forcing someone to minimize it manually — and underneath, the real pop-up was still sitting there unanswered, so they had to answer it a second time. The cause was two separate bugs. First, on Windows, a computer program isn't normally allowed to bring its own window to the front unless it's given special one-time permission — Conxa was only asking for that permission once, right when recording started, instead of every single time it needed to bring the browser window back to the front after a pop-up closed. Second, if an answer somehow arrived for a pop-up that had already changed or moved on, the system used to just silently throw the answer away with no record of it happening, making bugs like this nearly impossible to track down. Both are fixed now: Conxa asks for that permission every time it needs it, and any dropped or failed answer now leaves a clear trace instead of vanishing. Also added tests so this exact failure pattern can't quietly come back.
— 2026-09-03

## A confusing "element not found" message during self-healing now explains itself instead — 2026-09-03
When a workflow can't find something it's supposed to click and asks the AI assistant for help fixing it, the assistant is supposed to reply with its pick for what to click instead. If it forgot to include that pick and just asked the system to "carry on," the system used to quietly restart from a blank browser tab and report a misleading "couldn't find it" — as if the button had genuinely vanished, when really the assistant just hadn't answered the question yet. Now it gives a clear message instead, saying a decision is still waiting and exactly what's needed to provide it, and it keeps the paused page ready so the very next attempt can still succeed. Found and fixed while running the recovery-testing checklist.
