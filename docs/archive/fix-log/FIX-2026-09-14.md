# Fix Log — 2026-09-14

## Finished the "AI Review" checkpoint feature: it can now actually be built and tested, not just recorded on paper — 2026-09-14
A workflow can now pause partway through, show Claude the current screen, ask it a question the workflow's author typed in ("is there an error banner on this page?"), and use the answer to decide what happens next. The engine that runs this on a customer's computer was already built in an earlier update, but nobody could actually create one of these checkpoints — there was no button for it in the Build Studio, and there was no way to test a workflow containing one before shipping it, because the test run had nobody to answer the question. Both gaps are now closed. A new "AI Review" option appears when adding a step, with a question box, a few one-click answer-shape presets (yes/no with a reason, a single answer, or "accept anything"), and a choice for what happens if a usable answer never comes back (stop the run, fall back to a default, or keep going). And when a builder tests a workflow with one of these checkpoints in it, the Build Studio now answers the question itself using its own AI connection and keeps the test running, instead of the test just failing outright. The checkpoint also now sees the same list of on-screen buttons and fields the recovery system already looks at, not just a picture of the page, so it can reason about the page more reliably.

## Fixed a sign-in that "didn't take" for group workflows until the app was restarted — 2026-09-14
A workflow that belongs to a group of connected apps (for example, an "Enterprise" folder that needs both Salesforce and Google Drive) could get stuck saying it still needed a sign-in, even right after the person had just signed back in successfully. Running the test again showed the exact same "please sign in" message — but simply restarting the Build Studio app made it work perfectly. The cause: the app keeps two copies of a saved sign-in on disk — a secure, locked copy and a plain backup copy — and it was always trusting the secure copy, even when the plain backup was the newer, correct one written moments earlier by the fresh sign-in. Only a restart happened to force the secure copy to be refreshed from the backup. Now the system always checks which copy is actually the newest and uses that one, refreshing the secure copy on the spot — so a fresh sign-in takes effect on the very next run, no restart needed.

## Fixed "something went wrong" when attaching a recording screenshot to a step inside a loop — 2026-09-14
In the workflow editor, picking a screenshot from the recording to attach to a step (or clearing one, or picking a different moment-in-time frame) would fail with a generic error, but only for a step that lives inside a "repeat for each" loop. This turned out to be two separate problems layered on top of each other. First: the app knew which loop step the person had selected on screen, but when it saved the change it only ever told the backend which loop the step belonged to, not which specific step inside that loop — like addressing a letter to an apartment building but leaving off the unit number. The backend would then try to apply the change to the whole loop instead of the one step inside it, and reject it. Second, once that addressing problem was fixed, a deeper issue surfaced: building the picture the system studies to recognize that element again was silently missing some of the photos it needed, so it failed anyway — and that failure was showing up as an unhelpful "something went wrong" instead of a clear explanation. Both are now fixed: the app sends the full, specific address for a step inside a loop, the missing photos are included again, and if this step ever does fail for a real reason, the person now sees an understandable message instead of a scary generic crash. This only affected steps inside loops; regular steps were never broken.

## Quieted a harmless but scary-looking error message during recording — 2026-09-14
While recording a workflow in the Build Studio, closing a browser tab at just the wrong moment could print a long, technical-looking error in the developer logs — something about a "closed target" and a task exception. Nothing was actually broken: the recording had already captured what it needed, and only a background cleanup message (delivering a receipt back to a page that was already gone) failed to send. That specific, expected message is now silenced so it doesn't look like a crash; any other, genuine error still shows up as before.

## Finished the compiler cleanup: a compile now shows when a background helper failed, and corrupted files can't silently vanish or lose data — 2026-09-14
This finishes yesterday's cleanup of the automation compiler. First, a compile report can now honestly say "something needs a second look" — before this, if a background double-check step (the "second opinion" that reviews a whole recorded automation) failed to run at all, the report looked exactly as clean as one where that step succeeded and found nothing wrong. Now a genuine failure is flagged, so a reviewer can tell the two apart instead of trusting a report that quietly skipped a safety check. Second, a caching bug that could get permanently stuck is fixed: three spots used to save a fallback guess into their memory as if it were a real, confident answer — meaning one brief network hiccup could make the system keep using a worse guess forever for that same situation, never trying again for a real answer. Third, we looked at fully rebuilding how a finished automation package gets assembled (removing an old two-copy system), but discovered along the way that a real screen in the Build Studio — the one that lets a builder browse a compiled package's files — depends on exactly the files that rewrite would have deleted. So instead of a risky rebuild, we fixed the actual problem: a handful of spots that would quietly ship a package missing pieces (like its drift-detection fingerprint or a linked backup automation) if one of its files got corrupted moments after being written, instead of stopping and saying so. Finally, several places that manage saved automations, groups, and settings will now speak up with a clear warning if a saved file turns out to be corrupted, rather than quietly acting as if that item never existed. Several other spots that looked like bugs during this work turned out, on closer inspection, to be intentional and already correct — those were left alone rather than "fixed" into something worse.

## Cleaned out old leftover code from the automation compiler and made several silent failures speak up — 2026-09-14
The part of the system that turns a recording into a working automation had built up old, unused code over time — like a garage full of tools nobody uses because the job they were bought for doesn't exist anymore. Some of it was harmless clutter (about 250 lines removed with no change in behavior, all double-checked against the full test suite before and after). But one piece was an active problem: a leftover step from an old version of the system was still running every time someone renamed an automation package or one of its automations, and it would quietly overwrite that package's correct instructions file with an outdated one describing a completely different, no-longer-used way of running automations — a customer or teammate opening those instructions after a rename would have been told to do something that doesn't apply anymore. That's now removed. Separately, several places that should have raised a clear error when something went wrong — a missing software component, a corrupted settings file, a corrupted automation-pack file — were instead quietly working around the problem and continuing on with a degraded result, with nothing to indicate anything was wrong. Those spots now fail loudly and say exactly what broke, so a real problem gets noticed and fixed immediately instead of surfacing later as a confusing, hard-to-trace symptom. This is the first half of a larger cleanup; the remaining, riskier half (a bigger rewrite of how the finished automation package gets assembled) is written down as future work, not yet started.
