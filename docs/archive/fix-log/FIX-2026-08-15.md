# Fix Log — 2026-08-15

## Fixed "Invalid bundle name" blocking every package build after approving Human Edit — 2026-08-15
Clicking Approve on a reviewed workflow always failed with an error naming an invalid package, and it kept happening on every retry. The cause: the part of the system that names a company's package had started separating words with dashes, but the part that checks the name only allows underscores — so it was rejected every time, like a mailroom refusing any envelope with a dash in the address. The very first attempt had already saved that bad name to disk before the check caught it, so simply fixing the naming rule wasn't enough — every later attempt kept reading back the same broken name. Two things changed: the naming rule now always produces a name the checker accepts (including names starting with a number, like "1Password"), and any old broken name already saved on a machine is automatically corrected and cleaned up the next time it's read, with no manual fix needed.

## Fixed vision-based element detection quietly going dark during long compiles — 2026-08-15
When compiling a recorded workflow, one of the AI helpers — the one that looks at a screenshot to figure out where a button or field actually is — would sometimes hit a "slow down" response from its AI provider. When that happened, the whole helper would go silent for the next full minute, and every single step compiled during that minute silently fell back to a weaker, guess-based way of finding elements instead, with no visible warning that anything had gone wrong. It's like a GPS that loses signal for a red light and then just stays lost for the rest of the drive instead of reconnecting. Three things changed: the system now waits only as long as the AI provider actually asked it to wait, not a full minute by default; if every AI helper is briefly busy, it now pauses for a few seconds and tries again instead of giving up immediately; and the screenshots sent to the AI are now always shrunk down first, which means fewer "slow down" responses in the first place. The compile report also now tells you clearly how many steps, if any, had to use the weaker fallback, instead of that being buried and easy to miss.

## Fixed a technical warning that appeared in the background every time a confirmation popup opened — 2026-08-15
Every time someone opened a confirmation popup — like the "are you sure you want to delete this workflow?" prompt, the rename dialog, or the details panel on the side — a warning quietly appeared in the developer console (invisible to normal users, but visible to anyone debugging). It didn't break anything visibly, but it meant the dimmed background behind the popup wasn't properly wired up to a technical detail the popup system uses to know when its fade-out animation has actually finished. Three of these popup types had the same small wiring gap; all three are now fixed the same way.

## Fixed compiling a workflow freezing forever with no error — 2026-08-15
Compiling a recorded workflow could freeze on the very first step and just sit there — no error, no progress, nothing to click. The cause: opening a group's page had started quietly re-checking every saved login in the background, by opening an invisible browser window for each one, and that invisible browser could itself get stuck open with nothing to close it — silently pinning down the whole app in the process. That background re-check has been removed from simply opening a page; checking whether a saved login is still valid now only happens right before recording, at the moment it actually matters, and it now has a hard time limit so a stuck check can never freeze the app again. The compile screen also now says exactly which step it's on while loading a recording, so if anything is ever slow again, it's obvious where, instead of a silent screen.

## Stopped a wrong "please sign in" message from blocking compiles in developer mode — 2026-08-15

The compile step was quietly asking for a real login token behind the scenes regardless of that setting. It now recognizes developer mode properly and lets compiles run without demanding a sign-in that was never supposed to be required.

## Fixed downloaded files overwriting each other, and a failed task making every later one worse — 2026-08-15
Two real bugs found in last week's break-testing are now closed. First, when a task downloaded several files that happened to share a name — three exports all called "invoice.pdf" — each one wrote over the one before it, and the task still reported that every file had arrived. Files are now given distinct names as they land, the way a computer names a second copy of a download, so twenty files means twenty files. Second, when a task failed, the allowance it uses to retry and heal itself was never given back, so running that same task again in the same sitting started with nothing left and gave up almost immediately — it looked like the product was getting worse the more you used it. That allowance is now reset at the start of every run, so a second attempt behaves exactly like a first one, with no need to restart the app. Both fixes come with automated tests so they cannot quietly come back.
 — 2026-08-15

## Redesigned the Workflows and group screens, and stopped compiles from being paid for twice — 2026-08-15
The Workflows screen used to show each business group as a small dark box holding almost nothing, so you had to open a group to find out what was in it. Groups are now drawn as actual folders — tab and all — four to a screen, each listing the workflows inside it and how far along they are, so you can read the state of the whole business from one screen. The two things you actually pay for, compile credits and the Human Edit pool, now sit at the top of both screens as cards showing how much you have left; before, they were tiny labels you had to hover to read, and they didn't appear on the Workflows screen at all. Inside a group, each workflow's five-step journey now sits on its own line as a connected path rather than five loose buttons crowded next to the name, with the one step you should take next picked out in the brand colour. The step everyone calls "Human Edit" was labelled "Review" here, so it's now called the same thing everywhere.
Separately, we found and fixed a real billing bug. Compiling a workflow takes you to a progress screen, and the work genuinely keeps running if you click away — but the screen forgot all about it, and coming back started the whole compile again from scratch and charged a second compile credit. Now the compile is remembered outside that screen: leave, come back, and you rejoin the one already running. Like a kettle that keeps boiling when you walk out of the kitchen, instead of starting over each time you look at it.

## Planned a new "ask Claude mid-task" step, and found we already built most of it — 2026-08-15
Right now a recorded workflow follows a fixed script: it cannot look at the screen and make a judgement call. That rules out a lot of real business tasks, which are full of small checks like "did that actually save?" or "is this the right customer?". This adds a fully specified plan for a new kind of step the author can drop anywhere in a workflow: it pauses mid-run, shows Claude the screen along with a question written when the workflow was built, and waits for a structured answer that the rest of the workflow then acts on. While writing the plan we discovered the hard part is already built — the system already knows how to freeze a live page, ask Claude about it, and pick up exactly where it left off, because that is how it heals itself when a step breaks. So this is mostly teaching an existing trick a new purpose rather than new machinery. The plan also settles the tricky part: the workflow cannot simply "wait" for Claude the way it waits for a web page, so it has to hand the question over and be woken up with the answer, and it spells out what happens when the answer is late, malformed, or never comes.
 — 2026-08-15

## Fixed a broken wildcard, replaced raw web addresses with app names, and added an automatic "are you still logged in?" check — 2026-08-15
Three fixes to the Applications feature on the Group page (the place where you connect Salesforce, Render, and similar tools so a workflow can use them). First, the "any page after this one counts as logged in" shortcut — written as `site.com/{}` — was silently broken: it never actually matched anything, so the login window sometimes wouldn't close itself the way it's supposed to. That's fixed. Second, each workflow used to show the raw web address it starts on, like a stray note stuck to the workflow's name; it now shows the name of the connected app instead, so "Create a Lead" shows a small "Render" tag rather than the leftover `dashboard.render.com/login` text. Third, and most importantly: signing in once doesn't mean signing in forever — sessions expire. Now, every time you open a group, the app quietly checks each connected app's saved sign-in in the background using an invisible browser window, the same way a bank app silently checks if you're still logged in. If one has expired, that app's row turns red with a "Reconnect" button instead of quietly pretending everything's fine, and starting a new recording is blocked until you sign back in — so a recording can never run against a session that's secretly gone stale.
 — 2026-08-15

## A recording can now open a new tab, work there, and come back — and it actually replays correctly — 2026-08-15
Until now, if you opened a new browser tab while recording a workflow — either by clicking a link that opens one, or by pressing Ctrl+T yourself — everything you did in that new tab still got recorded, but the computer had no idea a tab switch had even happened. So when the workflow ran later, it kept clicking around in the *first* tab the whole time, either failing outright or, worse, clicking on the wrong thing that happened to look similar. This is now fixed properly. Every recorded click, type, or scroll now remembers which tab it happened on, and the finished workflow includes a clear "switched to a new tab" marker wherever that happened, so the step list actually reads like the recording did. When the workflow runs, it follows the same tabs: it waits for a tab the website is expected to open on its own, or opens one itself if you're the one who opened it manually with Ctrl+T. As part of the same piece of work, a file downloaded in one tab can now be picked up and uploaded again in a later tab, in that same run — before, that only worked by asking Claude to hand the file across by hand, one extra round-trip per file. The workflow editor also now shows a small "Tab 2 — sitename.com" divider in the step list wherever a workflow crosses into a new tab, so it's visible at a glance, not just something happening invisibly underneath.
 — 2026-08-15

## Fixed a leftover browser tab quietly staying open after a background task finished — 2026-08-15
A small follow-up to the new tab-switching support above. When a background task (one running without a visible window) opened a second tab, finished successfully, and handed control back, that second tab used to just... stay open, unseen, using up memory, for as long as that background browser stayed warm and ready for the next task. It's like leaving a spare room's light on after you've left the house — small on its own, but it adds up if it happens every time. Every task now closes any extra tab it opened once it's done, whether the task succeeded, failed, got cancelled, or needed the user to sign back in — so nothing gets left behind regardless of how the task ends.
 — 2026-08-15
