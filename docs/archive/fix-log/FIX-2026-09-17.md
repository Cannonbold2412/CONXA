# Fix Log — 2026-09-17

## Conxa Execute's release publishing no longer fails outright on a one-off hiccup — 2026-09-17
When Conxa Execute publishes a new release, it uploads a few files to GitHub — the installer, and some small support files. Every so often GitHub itself briefly stumbles partway through that upload, and the whole release used to fail and need a person to manually re-run it. It's like a delivery driver giving up after one closed gate instead of trying again a minute later. Now the upload automatically tries again a couple of times before giving up, so a brief hiccup no longer stops a release.

## Fixed a confusing startup message that blamed your plan when the real problem was the internet — 2026-09-17
When Build Studio couldn't reach Conxa Cloud on startup — say, on a bad connection — it showed a message claiming Conxa Cloud couldn't confirm your plan, even though your plan was never the issue. That happened because one shared piece of code used the "can't check your plan" label for every kind of connection failure, not just plan-related ones. It's like a delivery app blaming your payment method when the real problem is that it simply couldn't reach the server at all. The message now correctly says the connection failed, so people aren't sent chasing a billing problem that doesn't exist.

## Simplified how the AI reasoning setting is handled, removing an unnecessary workaround — 2026-09-17
Right after the fix below this one shipped, we decided to go simpler still. The system used to try to tell some AI providers to turn off their "thinking out loud" step to save time and cost, then had to work around the providers that refused to allow that. Now it never asks any provider to turn that step off at all — it just lets each one behave the way it normally does. This removes the whole category of problem instead of patching around it, and keeps the code easier to maintain going forward.

## One AI provider's own rule was quietly breaking replies for everyone behind it — 2026-09-17
One paid AI provider Conxa can use always insists on "thinking out loud" before it answers and won't let that be turned off. The system was always asking it to turn that off anyway. When it refused, Conxa gave up on the whole request instead of quietly trying one of the other available providers — and it kept making the exact same mistake on every later request too, so people using that reply feature kept hitting failures. Now the system notices that specific refusal, stops asking that provider to turn its thinking off, and keeps trying the other providers in the meantime, so a request only fails if every option genuinely can't answer it.

## Fixed a chat conversation that could get permanently stuck after one garbled reply — 2026-09-17
Every so often, the AI behind Conxa Execute's chat would send back a slightly garbled internal instruction (not something a user would ever see directly). The chat noticed the problem for that one turn, but then kept that garbled piece sitting in the conversation's memory — so every message after that point failed the exact same way, forever, with no way to recover except starting a brand new chat. It's like a form with one bad handwritten field: instead of crossing it out and continuing, the whole form kept getting rejected and resubmitted unchanged. Now that piece gets cleaned up the moment it's spotted, so a single hiccup no longer breaks the rest of the conversation.

## When Conxa's AI assistant can't get an answer, it now says so instead of staying silent — 2026-09-17
If every AI provider behind Conxa Execute's chat failed to answer, the failure reason used to vanish completely — it never reached the error message shown to the person, and it was never written to any log either. Support would see only a generic "couldn't run that" with no way to tell what actually went wrong. Now that reason is included in the error and recorded in the server log, so a real outage can be diagnosed in seconds instead of guessed at.

## Conxa Execute's chat now streams its reply and shows its thinking as it works — 2026-09-17
The chat window in Conxa Execute used to sit frozen with a spinner until the whole answer was ready, then dump the entire reply on screen at once. Now the reply appears word by word as it's written, the same way a person typing would look. When the model is reasoning through a problem before answering, that reasoning now shows up live too, in a dimmer "Thinking…" block above the final answer, so a user can see it's actively working instead of wondering if it's stuck. Nothing about billing or the final saved conversation changed — this only changes what's visible while a reply is being generated.

## Final pass on the cloud cleanup: merged duplicated code that had spread across many pages — 2026-09-17
Last part of the cloud-service cleanup — no behavior changes for anyone using the product, just tidying that makes future changes safer. Several small pieces of logic — formatting a date, formatting a dollar amount, turning "member_role" into "Member Role" for display — had each been separately hand-copied into seven or more different screens over time, with small differences that had started to drift. They're now written once and reused everywhere, so a future fix to "how dates are shown" only has to happen in one place instead of being remembered across a dozen files. Two nearly-identical confirmation popups (one for releasing a new version, one for rolling back to an old one) were merged into a single shared building block. And a stray piece of billing code that lived in the wrong part of the program — it belonged with the rest of the security/signing logic, not tucked inside the analytics code — was moved to where it actually belongs, closing out this cleanup effort.

## Fixed a payment webhook that could quietly lose a customer's payment, a broken deploy health check, and a handful of other places that were failing silently — 2026-09-17
Part three of the cloud cleanup, focused on problems that used to fail quietly instead of speaking up. The biggest one: when a customer paid for a subscription upgrade or a credit top-up, the payment provider's confirmation message could occasionally fail to process on our side — and until now, we told the payment provider "all good, thanks" anyway, which meant it never tried sending that confirmation again. A customer could pay and never receive what they paid for, with nothing anywhere to say so. Now we only confirm receipt once it's actually processed, so a failure gets retried automatically instead of silently dropped. Separately, we found that our own deploy system's "is this server healthy?" check would have been blocked by the same login wall as the rest of the site in a production-style setup — like a fire inspector being asked to show ID at a door that's on fire. That's fixed. A payment checkout page was also silently defaulting to a fake stand-in email address whenever a real one wasn't explicitly passed in — which, it turns out, was every single time, because the button that starts checkout never sent one; every subscription created this way was invisibly tied to a fake identity rather than the actual paying customer. It now uses the signed-in person's real email instead. Several other spots that used to quietly guess a "reasonable-looking" value when something was missing or broken — a workflow count showing zero instead of "unknown", a corrupted settings file being treated as brand new, a sync check silently starting over instead of reporting what actually happened — now say so plainly or write it to the server's records, instead of presenting a guess as fact.

## Error messages from the cloud service now read like sentences, and every failure leaves a trail — 2026-09-17
Part two of the cloud-service cleanup. Before, when something went wrong, both the online dashboard and Build Studio would sometimes show a short computer code instead of an explanation — someone hitting a seat limit would see the literal words "seat_limit_exceeded" instead of "this workspace is full." Now every one of those codes has a matching plain-English sentence, and the dashboard shows it instead of the code. Separately, if something broke in a way nobody anticipated, the old behavior was a blank, unhelpful error with no way to trace what happened — like a jammed vending machine with no error light. Now every such failure is written to the server's own records with a reference number, and that same reference number is shown to whoever hit the error, so a support conversation can start from "here's exactly what happened" instead of "it just broke." A few error messages that were quietly stitching a payment company's raw internal response text into what the customer sees have been cleaned up so they show the same plain sentence instead. Nothing about how the service actually behaves has changed — this only changes what a person sees when it goes wrong.
Started a bigger cleanup of the cloud service (the part that handles publishing, billing, and the online dashboard). First fix: the list of past installer builds on the Build Installer page has never actually loaded — it was quietly asking the server for a web address that didn't exist, like dialing a phone number with a digit missing. That's now connected correctly. Second: a matching "new-style" version of that same address, and one other like it, were wired up but could never actually be reached — a duplicate, older address was always answering first, like two people assigned the same desk where only the first one who sits down ever gets asked anything. That's fixed too. Alongside these fixes, a stack of code nobody was using anymore got cleared out: an old wiki-building script left over from a different project, a testing tool flagged by its own instructions as out of date, six page pieces and one whole file the interface never actually displayed, and three unused external add-ons those page pieces had been dragging in behind the scenes. None of this changes what anyone sees or does today — it just means less unused weight to carry forward, and one broken page now works.

## A rare seat-limit check no longer crashes with a blank server error — 2026-09-17
On the very first request from a brand-new person on a workspace that's already full, an internal seat-availability check could fail in a way that produced a generic, unhelpful server error instead of a clear "workspace is full" message. This was mistakenly reported as the fix for a separate, unrelated "Could not load telemetry" report — it wasn't, and never could have been, since it doesn't touch how that message gets chosen. It's still a real, worthwhile fix on its own: a full workspace now gets told clearly why a new person can't get in, instead of a confusing crash.

## Conxa Execute no longer has its own separate account system or backend — it now runs entirely on the same one as everything else — 2026-09-17
Conxa Execute used to be its own little island: its own sign-in system, its own payment setup, its own way of letting people pay with their own AI key. That meant extra accounts to create, extra bills to pay, and a clunky "type in this code" step for anyone a company wanted to give access to. All of that is gone. Execute now signs in with the exact same company account as everything else, its cost comes out of the same shared credit balance a company already has, and giving someone access is as simple as inviting them by email — the moment they sign in, they're in, no code to copy or paste. A signed-in person can also now switch between using it on their own or on behalf of a company they belong to. One loose end remains: a couple of one-time account-setup clicks still need to happen before this goes live, tracked so nothing gets missed.

## Conxa Execute cleaned up: dead code removed, and several places that used to fail silently now tell you what went wrong — 2026-09-17
Conxa Execute had grown some leftover parts and a habit of hiding errors instead of showing them. We removed a large chunk of unused reference code that was never actually running (about 60 files copied in "just in case" for a future upgrade, and a whole set of screens and buttons that could never actually be reached), which makes the app smaller and easier to maintain without changing how it works. More importantly, we fixed several spots where something going wrong used to look like nothing happening at all: if the app failed to start up properly it used to show a permanently blank window with no explanation — now it shows a real message and a Retry button. If the list of available skills failed to load, it used to just say "no skills installed" as if that were the truth — now it says the actual problem occurred, instead of a wrong but confident-sounding answer. A corrupted history file used to get silently wiped and replaced with a blank one — it's now set aside instead, so nothing is lost. We also closed a real billing safety gap: one of the payment-confirmation messages from our payment provider could previously be accepted without checking its signature, meaning a forged message could have looked genuine — every payment confirmation is now always checked.

## Clicking "Sign in" in Conxa Execute now tells you why it isn't working, instead of doing nothing — 2026-09-17
In the first real installed copy of Conxa Execute, clicking "Sign in with CONXA" did nothing at all — no message, no browser window, nothing. That's because the sign-in system for this particular app hasn't been fully connected on the company's end yet, but the button was designed to only react on success and stayed silent on any failure, like a doorbell that's wired up but not yet hooked to a chime. It now shows a plain message explaining sign-in isn't set up yet, in both places the button appears. Actually finishing the sign-in connection is a separate step that needs a company account to be created and linked in.

## Conxa Execute can now be installed as a real Windows app, not just run from source — 2026-09-17
Until now, the only way to use Conxa Execute was for a developer to check out the code and start it by hand — there was nothing to actually give a customer. Now there's a proper installer, built the same way Build Studio's already is: download it, click through a quick setup, and it puts a normal desktop app on your machine with its own icon and Start Menu shortcut. It also updates itself quietly in the background — when a new version comes out, it downloads next time you're online and finishes installing the next time you close the app, with no pop-ups or prompts to deal with.

## Conxa Execute now shows the browser inside the app itself, instead of popping open a separate window — 2026-09-17
Running a skill from Conxa Execute used to open a whole separate Chromium browser window that sat on top of the app, disconnected from the chat. Now, when a skill runs, a panel slides in on the right side of the same window and shows the live page there — chat on the left, the browser working on the right, one window instead of two. It's fully interactive: you can click and type directly in that panel the same as any browser. If several skills run at once, each gets its own tab inside that one panel instead of its own window. This landed in two parts today: first the skill-running part, then signing in to a website and handing control to a person mid-run — both of those also now happen right in the same panel instead of opening their own window. Every other way of running a skill (Claude Desktop, scheduled runs) is completely unaffected — they still work exactly as before, and if anything goes wrong showing the panel, the run quietly falls back to the old separate-window behavior instead of failing.

## Build Studio and Conxa Execute can sign in to the live service again — 2026-09-17
Opening Build Studio showed "Can't reach Conxa", and Conxa Execute stayed stuck on "Waiting for Execute access", even though the login itself had worked. The server keeps a guest list of apps it trusts, but it only knew how to read the name tag worn by the website — the desktop apps wear their name tag in a different spot, so the server turned them away every time. The server now reads the name tag from either spot, so both desktop apps are let in as long as they are on the guest list.
