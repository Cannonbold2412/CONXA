# Fix Log — 2026-07-14

## Fixed "Chromium installation failed (code 1)" with no details when installing a dev build — 2026-07-14

A user installed a Build Studio dev installer and got a dialog saying the browser engine
("Chromium") failed to install, with no useful reason given — just an exit code and a suggestion
to re-run a command that also gave no details.

The real problem: earlier in the day, some code that used to live inside the main runtime file
was split out into its own file (`page_scripts.js`, see the "scroll step" fix above). The local
build script that packages up the runtime for testing was updated to include this new file — but
the copy of the runtime already sitting on this machine (installed by an earlier build, before
that file existed) didn't have it. When the runtime started up to install the browser, it tried
to load that missing file first, crashed immediately, and exited — before it ever got to the part
that actually installs the browser or writes down what went wrong. That's why the dialog had
nothing to show.

Nothing was actually broken in the code — the fix already existed, it just hadn't been rebuilt
into this machine's installed copy yet. Re-ran the local build script to produce a fresh copy of
the runtime with the missing file included; next installer build + reinstall will pick it up and
the browser install should complete normally.

## Cleaned up the Build Installer page and fixed a package showing as "No package" — 2026-07-14

A user pointed out two things on the Build Installer page: after a successful build, technical
details (file paths, version numbers, cloud URLs) were dumped in a flat list with no visual
hierarchy, and if you left the page and came back, the confirmation that an installer was built
disappeared — you'd only see a small "Complete" label, with no clear way to tell "is this thing
built or not, and how do I download it." Separately, one package in the sidebar was showing up
labeled "No package" even though it had a working installer.

The "No package" label turned out to be a display bug: the sidebar was computing a package name
from an internal build folder path instead of just showing the name the user actually gave the
package when they created it — and when that computed name failed, it fell back to the literal
words "No package." Fixed by showing the package's real name directly instead.

For the Build Installer page itself: added a clear "Installer ready" card with the file name,
version, and build date, always visible whenever an installer exists — whether it was just built
in this session or built earlier and loaded back in when you return to the page. The Download
button now lives front-and-center in that card. All the technical details (file paths, cloud
URLs) moved into a collapsed "Build details" section that's still one click away, but no longer
cluttering the main view.

## Fixed workflow runs crashing on the "scroll" step with `ReferenceError: ak is not defined` — 2026-07-14

A user reported a run failing at a scroll step with a confusing error: `page.evaluate:
ReferenceError: ak is not defined`, deep inside the browser engine's own error stack.

The runtime app is obfuscated (scrambled) before it ships, both for real customer builds and
for local Studio testing, so the code is harder to read if someone gets hold of it. Two of the
scrambling settings work by rewriting a function to look up its real logic through a shared
helper defined elsewhere in the file — which is invisible outside Node.js. A handful of small
functions in the runtime (the ones that scroll the page, check if a button is scrollable/
disabled, and read the list of visible buttons/links) don't run in Node.js at all — the browser
automation library ships their source code straight into the actual web page and runs it there,
where that shared helper doesn't exist. So the scrambling silently broke those specific
functions; most of them fail quietly and just returned "I don't know" instead of a real answer,
but the scroll one had no such safety net and crashed the whole run outright.

Fixed by moving all of those browser-side functions into their own new file
(`runtime/page_scripts.js`) and scrambling only that one file with the two problem settings
turned off, while everything else in the runtime keeps full scrambling as before. Also updated
both places that build the runtime (the real release pipeline and the local dev build script)
so they stay in sync, plus the automated test harnesses that stage a copy of the runtime files.

## Found and fixed why some step edits (like a "Value" field) silently didn't save — 2026-07-14

A user reported: they edited a step's Value field on the Review Selectors page, clicked
Continue, then Apply, then Approve — and when they came back to that step, the value hadn't
actually changed. They asked directly: is this even being written to the file?

Traced it all the way down with a live test that writes and re-reads the saved file exactly the
way Continue/Apply do — confirmed the file-writing part has always been correct. The problem was
one level up: the edit was never being *sent* to be saved in the first place, and nothing told
the user that.

The step-editing form quietly refreshes itself from the latest saved data whenever that data
changes underneath it — which is normally fine, except it did this unconditionally, even in the
middle of someone typing. Two ordinary things can trigger that refresh while you're still
editing: switching away from the Build Studio window and back (a routine background refresh),
or saving something else on the same page, like the Recovery search hints card that sits right
next to the Value field. Either one would quietly wipe out whatever you'd just typed and reset
the form's "you have unsaved changes" flag back to clean — so when you hit Continue, the app
correctly saw nothing unsaved and skipped saving, with no warning shown.

Fixed by making that refresh skip itself whenever there are edits in progress, so it only
kicks in once your changes are actually saved (or you switch to a different step entirely,
which still loads fresh normally). This affects every field in that form, not just Value —
so it also protects the intent/description, selectors, outcome checks, and other fields from
the same silent-loss pattern.

## Fixed the "re-target" edit wizard losing or mixing up changes between steps — 2026-07-14

The 3-page re-target wizard (pick the element → review its selectors → confirm the outcome
checks → Apply) is supposed to save everything from all three pages in one go when you hit
Apply. That final save was always working correctly — but the in-progress editing before it
had two real bugs, plus the error messages you'd see if something went wrong were unreadable.

**Bug 1 — edits from one step could leak into another.** The wizard keeps your in-progress
picks (the drawn region, the selector list, the outcome checks) in memory while you move
through its three pages. There was code meant to clear that memory out whenever you opened a
different step, but it was never actually being called. So if you started re-targeting one
step, then clicked over to a different step without finishing, the old step's picks could
still be sitting there — worst case, hitting a shortcut button on the new step could apply
the wrong region to it. Now switching steps properly resets the wizard.

**Bug 2 — silent loss of unsaved changes.** Because edits made on the "review selectors" and
"confirm outcome checks" pages aren't sent to the backend until you hit the final Apply
button (by design — that's what makes it one atomic save), clicking away to a different step
before Apply just threw those edits away with no warning. Now, if you've made changes on
those pages and click a different step, you get a "keep editing or discard?" confirmation
first instead of silently losing your work.

**Error messages made readable.** Editing a step's other fields (its description, the URL
it navigates to, its outcome checks, and so on) is checked against a set of rules before
saving — e.g. "a destructive action needs an outcome check" or "this field isn't editable
for this step type." When a rule was violated, the message shown was a raw internal code
like `Patch rejected: consequential_step_requires_required_assertion`. Added plain-English
text for every one of these rules that's reachable from the editor today, so you now get a
sentence explaining what to fix instead of a code.

Verified: existing backend test suite for the re-target wizard still passes (23/23), and the
renderer's linter/typechecker are clean.
