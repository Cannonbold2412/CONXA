# Fix Log — 2026-09-12

## Automations can now repeat a set of steps for every row in a list — 2026-09-12
Until now, an automation could make a decision ("if this, then that") but it couldn't repeat itself — there was no way to say "do this for every pending order" or "update every customer in this list." Someone wanting that had to record the same steps over and over, once per item, which only worked for a fixed, known list. Automations can now be built with a real "for each" loop: point it at a table or list, and it repeats a set of steps once per row, always double-checking it's acting on the correct row and never accidentally acting on the wrong one. Because a loop combined with a risky, hard-to-undo step is exactly the kind of thing that could go wrong at scale, this was shipped together with three safeguards: a hard limit on how many rows it will ever touch in one run, a way to preview the whole loop without actually clicking anything (see the "dry run" entry just below, which this builds on), and a requirement that anyone using a loop with a risky step must specifically confirm which row it's allowed to act on before it can be shared with customers. Building this required carefully reorganizing how a single step gets carried out internally, so that steps running inside a loop get all the exact same safety checks and error recovery that a normal step gets — nothing about how safely one step runs was allowed to be a "lesser" version just because it's inside a loop. All 687 existing automated checks were confirmed to still pass before and after that internal reorganization, plus dozens of new checks written specifically for the loop feature.

## Automations with a hard-to-undo final step can now be previewed before they actually do it — 2026-09-12
Some automations end with something you can't easily take back — deleting a database, sending a payment. Until now, the only way to see if the automation would work was to actually let it do that final thing. You can now ask it to do a "dry run" instead: it does everything up through the risky final step, confirms that final step's target actually exists on the page, and then stops — without ever clicking it. It tells you plainly what it held back. Separately, when someone builds an automation with a risky, hard-to-undo step buried in the MIDDLE instead of at the end, the system now quietly flags that during review — like a checklist reminder that the "point of no return" should usually be the very last thing, so an early hiccup leaves only a harmless unfinished draft instead of a half-finished mess. And a workflow can now optionally be linked to a "cleanup" companion workflow (like "cancel this draft") that gets offered — never run automatically — if something goes wrong partway through.

## Automations now warn you when they're running somewhere different than where they were recorded — 2026-09-12
If an automation is recorded on a big monitor in English by one person, and later run on a small laptop screen in German by someone else, buttons can end up hidden behind menus, or dates can be read in the wrong format — and until now, that showed up as a plain, confusing failure that looked exactly like the website itself had broken. Now, the system quietly notes the screen size, language, and time zone it was recorded in, and if the automation is later run somewhere meaningfully different, it adds a plain-English note explaining that — "this was recorded in English on a large screen; this browser is in German on a small one" — right alongside the result, whether the run succeeded or failed. We also noticed the system already knew how to detect a different kind of problem (the website's whole layout being redesigned since recording) but never actually told anyone — that warning was quietly logged and nothing more. Both warnings now reach the person actually running the automation, not just an internal dashboard.

## Automations now give a slow website one more chance before giving up — 2026-09-12
Two related reliability fixes, both about a website loading more slowly than usual. First: a handful of spots deep in the runtime that check the page (counting buttons, reading scroll position) had no time limit of their own, so if the browser ever froze — say, on a pop-up dialog it wasn't expecting — those checks could hang forever instead of failing cleanly like everywhere else already does. They're now all wired through the same safety timer the rest of the system uses. Second, and the bigger piece: today, how long a step waits before continuing is based on watching the page load exactly once, during the original recording — so a website that's simply having a slow morning can cause a step to fail in a way that looks identical to the website being broken. Now, right before giving up on a failed step, the system checks whether the page is still visibly changing (still loading content, still showing a spinner) and gives it one more try once things settle down — but only in a way that can never click a button twice by accident. A normal, fast-loading run is completely unaffected; this only kicks in on a step that was about to fail anyway. All 670 existing automated checks still pass, plus 12 new ones written for this.

## Fixed the two silent holes found in the compiler review — 2026-09-12
Two problems flagged earlier today are now actually fixed, not just written down. First: the compiler's "read the whole workflow and suggest improvements" step now gets real instructions and is correctly sent to a model that can look at pictures — it used to silently return nothing on every single compile, so every workflow was quietly missing this step's benefits (clearer variable names, catching a hardcoded value that should vary per run, flagging a step that does nothing) with no error anywhere. Second: workflows that target one of those "only draws what's on screen while scrolling" tables (common in big business software like inventory grids or long dropdown lists) can now find the row they need even when it hasn't been scrolled into view yet — the system scrolls the list itself, the same way a person would, instead of giving up and reporting a broken automation. Both fixes were checked against the full existing test suite (over 700 checks across the compiler and the runtime) with nothing broken, plus new checks written specifically to prove each problem is actually gone.

## Added four new items to the priority to-do list after an outside review of how reliable our automations are — 2026-09-12
An outside reviewer looked hard at how workflows stay working over time and flagged four gaps worth tracking. First: today we grade how "findable" a button or field is using a fixed table of guesses (a test-id tag is very trustworthy, plain text is less so) instead of actually checking — the plan is to simulate real website redesigns and measure which signals survive, turning guesses into evidence. Second: nothing today warns a customer when a workflow is replayed in a different language, screen size, or user role than it was recorded in — a change like that can make a working automation fail in a way that looks identical to the website having broken, so we're adding a plain warning for it. Third: the amount of time a step waits before continuing is based on watching the page load exactly once during recording, rather than watching for the page to actually settle down each time it runs — so a slow morning can cause a false failure. Fourth: workflows can currently make a decision (if this, then that) but can't repeat a step for every item in a list, which blocks a lot of everyday back-office work like "process every pending order" — this one is explicitly tied to also shipping a safe practice-run mode first, since looping combined with an irreversible action is exactly how automation software can damage real data. No code changed; all four are now written down as prioritized future work.

## Found two silent holes while reviewing how the compiler works — 2026-09-12
A full read-through of the compiler turned up two problems that nothing would ever complain about, so both are now written down as work to do. First: the compiler's "read the whole workflow and suggest improvements" step is being sent to the AI with no instructions attached and pointed at a model that can't look at pictures — so it quietly returns nothing, every single time, and the compiler falls back to its rules alone without ever saying so. It's like mailing a reviewer a thick envelope with no cover letter. Second: there's a setting for "this row lives inside a scrolling list that only draws what's on screen" that nothing ever fills in and nothing ever reads — so on those kinds of tables (common in big business apps) a workflow fails in a way that looks exactly like the website changed, when really the row just hadn't been scrolled into view yet. No code changed yet; both are now on the priority list.

## Compiling a recording was crashing partway through, every time — 2026-09-12
An earlier change had started combining two separate "review the workflow" steps in the compiler into one, so it could show the reviewer a screenshot alongside its notes instead of just text. That change was left half-finished: the compiler would get partway through, then hit a piece of code that was called but never actually written, and the whole compile would fail with an error instead of finishing. It's like a recipe that tells you to "fold in the sauce from step 9" when step 9 was never written. The missing piece is now written, so recordings compile all the way through again. While fixing it, we also found and fixed a smaller inconsistency: if that review step failed for some reason (a busy server, for example), the finished workflow could end up looking very slightly different than if the review step had been turned off on purpose — it should always look the same either way, and now it does.
