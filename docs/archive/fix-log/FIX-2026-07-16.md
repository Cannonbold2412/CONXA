## Found the actual cause of the missing iframe fields — a self-inflicted deadlock in how we reported them — 2026-07-16

One more recording attempt with all four timing markers from the last fix came back with something
we hadn't seen before: it proved every one of those four regular background checks completed fine,
every single time. So the freeze was never in any of them. But this attempt's evidence pointed
somewhere new — a piece of end-of-session bookkeeping showed that, deep in the browser, the Create
Contact panel had in fact become fully healthy and ready, exactly like every other part of the
page. It just never managed to tell us anything it captured.

That's the real story: whenever a form field lives inside a nested panel (an iframe), our tracking
script has to describe exactly where that panel sits on the page before reporting the typed value
back to us — think of it like a delivery driver who has to write down the full building/floor/unit
address before dropping off a package, whereas someone on the ground floor just walks straight in.
Writing down that address involves asking the browser several follow-up questions. The problem: we
were asking those follow-up questions at the exact moment we were still in the middle of receiving
the FIRST message — like answering a phone call by placing someone on hold to make a second call on
the same line, except this particular phone system can't handle that and simply never comes back.
Every message from inside any nested panel got stuck this way, permanently, the very first time it
happened — while anything typed directly on the main page (no address needed) always went through
fine, which is exactly why only nested panels were ever affected.

Fixed by no longer asking those follow-up questions while still on that first call. We now take a
message, hang up immediately, and only THEN dial back out separately to work out the exact address —
a completely different, safe moment to do it. Verified with an updated test that checks this
handoff still produces the exact same address details as before, just computed at a different,
safer point. Full test suite passes clean, no regressions.

This is the strongest, most complete explanation found across everything tried today — it matches
every single failed attempt, not just the specific slow-loading-panel cases the last several fixes
targeted. **Needs one more real recording to confirm it's the actual fix**, but this is the first
explanation that accounts for every clue gathered so far, not just some of them.

## Found the real freeze point: checking too early, right as a panel is still settling in — 2026-07-16

The fix from earlier today (skipping a redundant double-check) turned out not to be the whole
story — one more recording attempt still cut off exactly the same way, just a fraction of a second
earlier in the sequence. That earlier timing was actually useful: it showed the freeze happens the
very instant the Create Contact panel first appears on the page, before the tracking script even
gets a chance to try attaching to it.

Root cause: the tracking script does a quick check on a panel the moment it shows up, to see if it
needs attaching. For HubSpot's heavy panels specifically, that exact moment is when the panel is
busiest internally, still swapping itself in and out — and it turns out asking a panel a question
at that precise instant can, in rare cases, simply never get an answer back, with no error and no
timeout, freezing the entire recorder in place waiting forever for a reply that isn't coming. Every
single one of today's attempts landed on exactly this unlucky instant.

Fixed by giving every panel a short grace period (a third of a second) after it first appears before
the tracking script asks it anything at all. The panel's own built-in self-healing (already shipped
in an earlier fix, and confirmed working independently) still runs immediately and unconditionally
regardless — this only delays our side's extra confirmation check, which was the risky part, not the
panel's own real recovery. Full test suite passes clean, no regressions.

**Not yet proven against a real recording** — this is the second, deeper layer of the same underlying
issue and the strongest lead yet, but only a live attempt will confirm it's the last one.

## Fixed typed form fields inside an iframe going completely uncaptured (HubSpot "Create a Contact") — 2026-07-16

After yesterday's fix for iframe steps disappearing at compile time, the user re-recorded the same
HubSpot workflow to double-check it, and asked whether the new recording actually captured what
they typed inside the iframe. It hadn't: the recording had only 6 top-level clicks and not a single
typed field, even though the user confirmed they did type into the contact form.

This turned out to be a different, earlier bug — nothing to do with yesterday's fix. HubSpot loads
its "Create a Contact" panel inside an iframe whose content it swaps out using a technique
(`document.open()`/`document.write()`) that quietly replaces everything inside that iframe without
Chrome ever treating it as a real page navigation. Our recorder's tracking script normally
re-injects itself into iframes when they navigate to a new page — but this swap doesn't count as
one, so the script had no way of knowing the content underneath it had just been replaced, and its
click/typing listeners went along with the old, discarded content. There was a periodic safety net
meant to catch exactly this, but investigation found it could be fooled: it checked a marker left on
the page to decide "is my tracking script still attached here?", and that marker could survive the
swap even though the actual listeners didn't — so the safety net believed everything was fine when
it wasn't.

Fixed by having the tracking script watch for that swap directly (instead of relying on the
after-the-fact marker check) and immediately re-attach its listeners the instant it happens, right
there in the page, with no delay and no dependency on the periodic safety-net check succeeding.
Verified against a real Chromium browser and a real recording session, using a test page that
swaps its content the same way HubSpot does: before the fix, all typed input after the swap was
lost, exactly matching what the user saw; after the fix, it's captured correctly, including across
the same field being swapped and retyped more than once, with no duplicate entries.

## Removed browser-close as the thing that finishes a recording — 2026-07-16

The last two days of fixes (see below) were all chasing the same root problem from different
angles: Build Studio watches the recording browser and, the moment it thinks the browser closed,
automatically wraps up and saves whatever was captured so far. Every patch was really just trying
to make that "is it closed yet?" check harder to fool — first a 2-second grace period, then 8, then
20 — because a slow-loading page could still trick it every so often, and each time it got tricked,
part of the recording was silently lost.

Instead of continuing to tune that check, removed it as a trigger entirely. Closing the browser is
still the natural way to signal "I'm done," and the popup still tells you to do that — but it no
longer *does* anything by itself anymore. After closing the browser (or even before, if you'd
rather), you now have to explicitly click **Save Workflow Now** / **Save Session Now** to keep the
recording, or **Cancel** to throw it away. Both buttons already existed from earlier fixes and
already worked correctly no matter what the browser was doing, so this was mostly about deleting
the automatic trigger and updating the on-screen instructions to match, in both the Workflow and
the Login recording popups. A slow page can no longer destroy a recording — at worst it now just
delays a status message by a few seconds, which nobody will notice, since the real save only ever
happens when you ask for it.

## Fixed "Cancel" during a workflow recording leaving Build Studio stuck saying a recording is already in progress — 2026-07-16

A user recorded a workflow, closed the browser, then hit "Cancel" instead of "Save Workflow Now" (a button added
in yesterday's fix log). Clicking "Create Workflow" again right after that failed every time with "You already
have a recording in progress," even though no browser window was open anywhere.

The "Cancel" button added yesterday only cleared what the popup itself was showing on screen — it never told
the background process the recording was actually over. Behind the scenes, Build Studio deliberately waits
several seconds after a browser window closes before it fully believes the browser is gone (that patience was
itself a fix from yesterday, for a different bug where a slow-loading page inside the browser was mistaken for
the browser closing). Normally that's invisible — the popup waits it out and finishes on its own. But "Cancel"
skipped past that wait instead of resolving it, so the background process kept the recording marked as active
until its own slow check eventually caught up on its own, sometimes ten-plus seconds later. Any attempt to
start a new recording during that window was correctly, but confusingly, rejected as a duplicate.

Fixed by making "Cancel" (both on the Workflow popup and the matching Login popup) actively tell the background
process to stop and forget that recording right away, instead of just hiding it on screen and hoping the
background process catches up. Cancelling now also throws away the empty workflow placeholder that gets created
the moment recording starts, so a cancelled recording doesn't leave a broken entry behind either. Starting a new
recording immediately after Cancel now works every time.
