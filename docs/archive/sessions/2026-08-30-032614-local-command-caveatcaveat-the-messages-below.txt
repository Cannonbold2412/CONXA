  fit for learning. dedupe.py today is pattern-matched heuristics
  (drop_superseded_focus_events, collapse_select_interaction_noise,
  dedupe_scroll_events — all rule-based on event shape), and "is this step
  noise/should this be a variable/does this need a hover" are genuinely fuzzy
  judgment calls, not identity lookups. That's exactly why the invariant only
  locks down selector strings — the codebase already routes step-intent and the
  workflow intent graph through an LLM for similar reasons.

  So the split I'd hold: element targeting stays deterministic (auditable, must
  survive recovery/replay identically every run — an LLM guessing a selector
  differently each compile would break the whole self-healing story). But
  "what's a wasted moment," "should this be parameterized," "hover vs click" are
  classification decisions over recorded event sequences — good candidates for
  a learned classifier or LLM pass feeding into the deterministic pipeline
  (e.g., a step before dedupe.py/run.py that scores/labels events), not
  replacing it.

  Practical path: instrument these judgment points now (log what a human
  corrects in the editor — collapsed steps, retargeted hover,
  promoted-to-variable fields) as labeled training data, since you don't have it
  yet. Want me to sketch where in pipeline/run.py that labeling hook would go?

● Yes — hybrid, not either/or. Deterministic stays the backbone for anything
  that must be reproducible and auditable (selector generation, targeting,
  recovery matching — the stuff TRD.md's invariant protects). ML/LLM sits on top
  for the fuzzy judgment calls (dedupe/noise-filtering, variable detection,

  a classification problem, not a lookup — and only once you've collected real
  labeled data from human corrections, since guessing without data is worse than
  the current heuristics.

  large json and as output also we need large jason                             
● Don't reach for a seq2seq "JSON-in/JSON-out" generative model — that's the
  wrong shape for this problem and reintroduces exactly the
  non-determinism/hallucination risk you're trying to avoid (a generated JSON
  can drop fields, invent keys, or vary run-to-run). Reframe it: you're not
  generating a document, you're labeling elements in a fixed input (per-event
  tags like is_noise, promote_to_variable, interaction_type), then
  deterministically merging those labels back into the original JSON you already
  have.

  Two-phase path:
  - Now (no data yet): reuse the LLM router already wired into
    conxa_compile/llm/ with schema-constrained/function-calling output (most
    providers support forcing valid JSON against a schema) — zero new infra,
    works few-shot while you're still collecting labels via the BUILD-18
    instrumentation hook.
  - Later (once labeled volume exists): swap to a lightweight sequence-tagging
    model over engineered per-event features (event type, DOM depth, time-delta,
    selector signal quality, etc.) — a small transformer tagger or even
    gradient-boosted trees per event. Cheaper, faster, easier to keep
    near-deterministic than any large generative model, and it only ever emits
    labels, never raw JSON structure.

  The "large JSON out" requirement mostly disappears once you stop treating this
  as generation and start treating it as classification-then-merge.
